# Impeccable Design Context — ShoppingClaw Web

> 本文件由 impeccable 技能的 `teach-impeccable` 流程生成，作为本项目**所有前端设计决策的唯一依据**。
> 修改设计方向时，先改这里，再动代码。

---

## Design Context

### Users

两类使用者，同一套界面，诉求不同：

1. **自用（主用户 = 项目作者本人）**
   - 场景：带着一个模糊的购物需求进来（例："预算 5000 给爸妈买台洗地机，要静音好打理"）。
   - Job to be done：把它拆成可执行的判断——搜商品、比参数、看评价风险、拿到一个**带证据链的推荐**；
     以及长期挂着的六类主动监控（价格 / 库存 / 优惠券 / 排名 / 店铺活动 / Agent 主动总结）。
   - 使用状态：会反复回来、会长时间停留、会盯着 Agent 推理过程看。**不是一次性访问。**

2. **演示（技术面试官 / 评审）**
   - 场景：短时间（几分钟）内判断这个项目值不值得深聊。
   - Job to be done：看懂"多 Agent 可追溯推理"到底强在哪——**派给了谁、拿到什么结论、证据是什么**。
   - 关键：他不会读代码，只会看界面。界面本身就是答案。

### Brand Personality

- **三个词**：精密 · 克制 · 有据
- **情绪目标**：**confidence（可信）**——让人相信这个系统给出的判断是有依据的。
  明确**不**追求 delight（俏皮愉悦）、**不**追求 urgency（紧迫促销感）。
- **语气**：像一个严谨的顾问，不寒暄、不夸自己、每句话都能追溯到来源。

### Aesthetic Direction

- **反参照（最重要）**：**通用 AI 聊天壳**——中间一个对话框、左右大片留白、和 ChatGPT 长得差不多、
  看不出这是一个购物决策产品。**这一条是当前界面的首要问题，任何改动都不得强化它。**
- **正面方向**：精密工具感（Linear 气质）——靠**排版层级、间距节奏、精确对齐**建立专业感，
  而不是靠渐变、发光、毛玻璃等装饰。
- **主题**：**浅色 + 深色两套**，共享同一套语义 token，切换平滑、不重排、不丢层级
  （现状已有 `src/assets/css/base.dark.css`，需重构成语义 token 驱动）。
- **配色禁忌**：
  - 弃用 Ant Design 默认青 `#13c2c2`（现 `--color-accent-500`）——它是"组件库默认脸"的主要来源；
  - 禁止紫蓝渐变、霓虹点缀、深色+发光这套典型 AI 审美；
  - 禁止毛玻璃滥用、圆角+通用阴影的无差别套用；
  - 彩色左边条 callout 卡、胶囊（pill）标签堆砌、用彩色容器表达层级——同属典型 AI 产品的装饰语法。
    层级一律用排版（字号/字重/颜色深浅）与发丝线表达；彩色只用于语义状态文字与关键数据（如成交价）。
- **字体**：建立独立字体系统（展示字体 + 正文字体 + 数据/等宽字体三档），
  弃用 Inter / Roboto / Arial / Open Sans 这类默认栈。

### Design Principles

1. **证据优先于对话（Evidence over chat）**
   界面的主角不是对话框，而是 **Agent 派发轨迹 + 证据链**。聊天只是输入入口。
   现状已有 `AgentFlowPanel` / `ThinkingProcessSidebar` / `ToolCallCard`，应把它们从"侧边附属"
   提升为**视觉重心**。

2. **可追溯必须看得见**
   「派给了谁 → 拿到什么结论 → 依据是什么」这三段必须在一个屏幕内可展开、可回看。
   这是产品相对"单轮问答"的核心差异点，也是面试官唯一关心的东西。

3. **克制的专业感**
   信任感来自**精确**：对齐、间距节奏、字号层级、状态语义清晰。
   不使用装饰性渐变 / 发光 / 投影堆砌；动效只服务于状态变化，不用于炫技。

4. **信息密度，而非留白表演**
   购物决策需要横向对比参数（价格、规格、风险评分）。
   要能一眼扫到多维信息，**反对**为了"高级感"把内容稀释成大留白。

5. **双主题语义一致**
   浅色 / 深色只切换语义层 token（`--color-surface` / `--color-text` 等），
   原始色板保持不变；切换不得导致层级丢失或对比度不达标（WCAG AA）。

## 🔓 分区豁免：代购送礼 · 情境设计语言

**适用范围**：`/proxy` 的代购送礼智能体（当前实现为 `views/GiftBoxView.vue` 及其 `components/gift/**`）按本节执行。
其上各节中与本节冲突的条目，**对该分区不适用**。
（`/proxy/scroll` 是 v1 流式卷轴，仅作对照保留，不再是主实现。）

豁免的依据是**任务性质不同，不是审美偏好**：

|  | 采购规划 `/planning` | 代购送礼 `/proxy` |
| --- | --- | --- |
| 任务性质 | **决策收敛**：N 个候选 → 1 个方案 | **意义建构**：1 个意图 → 一段过程 → 1 份礼物 |
| 信息流向 | 横向汇聚 —— 必须并置才能比较优劣 | 单一对象生长 —— 必须「看得见改动」才成叙事 |
| 承载形态 | 固定分屏（执行流 / 决策图 / 待交付） | **单屏固定**（不滚动）+ 覆盖层承担步骤 |
| 对话位置 | **控制面**：独立输入区，持续会话 | **贴在物件上的批注**：气泡，无常驻输入框 |
| 用户心态 | 我是管理员，我要高效比价 | 我是送礼者，我在倾注心意 |

**v2 的两条硬约束（换了承载形态才成立，改动时不得破坏）**：

1. **页面高度恒定一屏**，不随推进增长。步骤——定制、清单、改动记录——一律进覆盖层，
   不在主页面追加区块。验收：推进到任意阶段后 `scrollHeight <= innerHeight + 2`。
2. **叙事区不允许变成可增长的列表**。右侧旁白固定最多 2 条（方向说明 + 最近一次改动），
   更早的下沉进「改动记录」覆盖层，只留计数。
   理由：v1 的失败正是「一条会变长的流」，把同一问题搬到侧栏不算解决。

### 放开的三条

1. **密度** —— 允许更大留白（见 `assets/css/gift.less` 的 `.gflow`，块间距 40px）。
   **对价（必须遵守）**：每一块都要携带实质内容。概念卡必须同时具备「氛围构成 + 概念解释 + 构成预览 + 预计总价」四项，
   **禁止只有标题加一张氛围图**。
2. **承载形态** —— 允许**单屏固定布局**（不滚动）与覆盖层（定制 / 清单 / 改动记录）。
   **对价（必须遵守）**：信息不得因为「要塞进一屏」而被删减 —— 放不下的改由覆盖层或右栏承载，
   不许出现「因为一屏装不下，所以砍掉几个构成项」这种偷懒。
3. **情境色** —— 允许暖金 `--second-*` 作主色，与采购的 emerald 形成身份区分。
   **仍禁止**用彩色容器表达层级；层级依然靠排版、留白与发丝线。

### 不放的五条（这几条与「感性」无关，是「AI 味」的来源）

1. **禁紫蓝渐变 / 霓虹 / 发光 / 毛玻璃滥用**。
   氛围一律用**色板 + 几何构成**表达，不用渐变与发光。
2. **禁无差别圆角 + 阴影堆叠**。卡片靠留白与色板分层，不靠阴影
   （`gift.less` 的 `.gcard` 只有 1px 描边，无 `box-shadow`）。
3. **禁纯留白表演** —— 见放开第 1 条的「对价」。
4. **禁黑箱**。每处推荐与每处替换都必须可解释：
   概念卡要说清「为什么这样搭」，物件的替换必须留下理由，并一路带到贺卡寄语与最终清单。
   这是「证据优先于对话」在情感语境下的翻译 —— **不是参数可解释，是心意可解释**。
5. **双主题、语义 token、零裸色值、对比度 ≥4.5:1、动效只服务状态变化** —— 全部不变。
   配色禁忌、字体系统、可追溯性要求同样不变。

### 素材约定（前提：项目当前没有图片生成能力）

`public/` 只有 `avatar.jpg` / `favicon.svg` / `login-bg.jpg`，全仓库无文生图能力。因此：

- **氛围图** → 色板 + 几何构成（`components/gift/MoodSwatch.vue`）。纯 SVG、零素材请求，
  且因为颜色取自语义化色板，天然适配浅色与深色两套主题（真实照片反而需要在两套主题下各自调色）。
- **包装纸纹理** → CSS 图案参数化（`data/giftDemo.js` 的 `wrapPatternStyle`），四种基础图案 × 色板。
- **贺卡字体** → 用现有三套字体做**排版风格**差异（字体族 + 字号 + 行高 + 字距 + 对齐），不引入字体资源。
- 将来若接入图像生成，只能作为**增强**，不得成为氛围图的唯一来源（否则离线与降级路径会断）。

## 与后端的接口面（前端改写时必须对齐）

- 聊天走 **SSE 流式**（`POST /api/chat/agent/{agent_id}`），事件序列：
  `init → thinking → tool_start → tool_complete → answer* → done`，另有 `title` / `error` 事件。
- 认证：`Authorization: Bearer <JWT>`；端点 `/api/auth/register`、`/login`、`/me`。
- 会话：`GET /api/chat/conversations`、`GET /{thread_id}`、`DELETE /{thread_id}`。
- 演示技巧：主动监控可调用后端 `trigger_now()` 立即触发一次，不必等 cron。
