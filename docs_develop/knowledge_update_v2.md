## 总体判断

v2 比 v1 有实质性进步，修正了三个核心问题（路由策略、中文适配、写入侧），如果作为中小团队的内部项目，基本可以落地执行。但还有几处细节在企业环境下会遇到真实阻力，逐一说明。

---

## 显著改进的部分

**并联召回替代串行路由**是最关键的修正，方向完全正确。`result_fuser.py` 承担多路结果合并的设计也是合理的工程分工。

**`source_type` 替代 `confidence` 数字**，这个判断非常务实。来源类型是确定的事实，置信度数字是主观估计，前者在团队协作和后期维护中争议少得多。

**写入侧的版本管理**加入了 `is_active` 标记和增量更新，这是 v1 最大的缺口，v2 补上了，方向对。

---

## 仍然存在的问题

### 问题一：result_fuser 的冲突处理过于简单

文档里的冲突处理逻辑：
> 如果 L2 返回了"禁止退货"的铁律，则直接丢弃 L3 中关于"如何退货"的建议。

这个例子选得太理想化。真实的冲突场景要复杂得多：

FAQ 说"电子产品7天无理由退"，规则库里同时存在"已激活设备不支持退货"——两条都是 `OFFICIAL_POLICY`，优先级相同，但结论冲突。用户的设备到底有没有激活，`result_fuser` 无法知道。

这类**条件性冲突**靠硬编码优先级解决不了，必须把冲突的多条结果都传给 LLM，让它结合用户的具体情况判断适用哪条。`result_fuser` 的职责应该是**检测冲突并标记**，而不是自动裁决。裁决权应该在 Agent 侧。

---

### 问题二：rule_engine 的 trigger_keywords 仍然是关键词匹配

```
rules (trigger_keywords[], applicable_category, condition_logic, action_content)
```

`trigger_keywords[]` 的本质还是关键词匹配，只是从 SQL LIKE 换成了数组包含检查。用户说"这个能换吗"、"我要申请售后"、"买错了怎么办"——这些表达里没有"退货"这个词，依然匹配失败。

企业里的规则引擎通常有两种成熟路径，二选一：

**路径A**：规则库只做精确条件匹配，用户 Query 先经过 NLU 层提取意图标签（`intent: refund_request`），用意图标签去匹配规则，而不是用原始文本。这样规则库不用关心用户怎么说，只关心用户想做什么。

**路径B**：规则条目也做向量化，和 L3/L4 共用向量检索，只是在 `source_type` 上标注为 `OFFICIAL_POLICY`，在 Rerank 阶段给予最高权重。这样天然解决了用语多样性问题，不需要维护 `trigger_keywords` 列表。

路径B的实现成本更低，和现有架构的融合度也更高，更适合这个项目。

---

### 问题三：增量索引的"计算 Chunk 差异"被低估了

文档写"自动计算 Chunk 差异，只更新变化的向量块"，这句话背后的工程复杂度被严重低估了。

Chunk 差异计算需要解决：文档修改后如何识别哪些 Chunk 变了（内容 hash 比对）、Chunk 边界变化时如何处理（一段内容修改可能导致后续所有 Chunk 的分割位置都偏移）、ChromaDB 的 upsert 用 `doc_id` 还是内容 hash 作为主键。

这三个问题每个都有坑。**企业里更常见的做法是按文档粒度全量重建**——当某个 Markdown 文件修改时，删除该文件对应的所有 Chunk，重新分块入库。虽然听起来粗暴，但实现简单、不容易出错，对于几百个文档规模完全够用。"精细化增量更新"是优化项，不是必须项，不应该在第一版里投入太多工程资源。

---

### 问题四：Phase 4 的 Prompt 注入设计有执行风险

```
你必须优先遵循 source_type: OFFICIAL_POLICY 的内容；
对于 USER_EXPERIENCE，请在回复中注明'根据过往用户反馈'
```

这个设计要求 Agent 感知 `source_type` 字段并据此调整行为，逻辑上合理，但有个前提：知识库返回给 Agent 的内容必须携带 `source_type` 标注，且 Agent 的 Prompt 里要有足够清晰的处理规则。

实际联调时常见的问题是：检索结果和 `source_type` 标注一起传给 Agent，但 Agent 在生成回复时忽略了来源标注，把 `USER_EXPERIENCE` 的内容当成官方政策输出。这不是 Prompt 写得不好，而是 LLM 在长 Context 里对结构化元数据的遵循度本来就不稳定。

更可靠的做法是**在 `result_fuser` 输出时就在文本层面做标注**，把 `source_type` 转化为自然语言前缀直接嵌入内容里：

```
【平台官方政策】电子产品7天无理由退换（未激活）
【历史用户反馈】该品牌客服响应普遍较慢，平均处理时长3-5天
```

这样 Agent 读到的是自然语言，不需要理解元数据字段，遵循稳定性更高。

---

## 一个缺失但关键的设计

两个版本都没有提到**知识库的评估机制**。在企业里，知识库上线后必须有持续的质量监控：

检索命中率（用户的 Query 能不能查到相关内容）、答案准确率（查到的内容是否真正解决了问题）、Bad Case 收集（Agent 给出错误答案时，是知识库的问题还是 LLM 的问题）。

没有这套机制，知识库的质量会在无感知的情况下慢慢劣化。这是企业知识库工程里被低估最多的环节。

---

## 综合评价

| 维度 | v1 | v2 |
|---|---|---|
| 召回架构 | 串行路由，有缺陷 | 并联召回，方向正确 |
| 冲突处理 | 未涉及 | 有设计但过于简单 |
| 规则匹配 | SQL LIKE，太弱 | keywords数组，改进有限 |
| 中文适配 | Levenshtein，不适用 | Embedding兜底，正确 |
| 写入侧 | 完全缺失 | 有版本管理，但增量索引被高估 |
| Prompt集成 | 未涉及 | 有设计但执行稳定性存疑 |
| 质量评估机制 | 无 | 无 |

**结论**：v2 可以作为工程实施的起点，Phase 1 和 Phase 2 可以直接按方案执行。需要在动工前修正两点：rule_engine 改为向量化方案（路径B），增量索引改为按文档全量重建。这两处改动能节省大量调试时间，避免在边缘情况上消耗工程资源。
