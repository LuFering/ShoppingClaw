## 核心诊断

### BASE_PROMPT 的根本问题

**决策树替代了推理**。用 `intent_confidence < 0.7 → 场景A → 严禁调用SubAgent → 必须澄清` 这样的硬分支，把 LLM 降级成了一个有限状态机。问题在于：

- 置信度 0.68 和 0.72 的处理路径完全不同，但 LLM 对这个边界其实有更细腻的判断力
- `缺口包含"product_list" → 调用 researcher` 是一张查找表，不是推理
- `description` 字段的模板格式强制 LLM 填空，而不是思考目标
- Step 1 → Step 2 → Step 3 的顺序约束，让 LLM 无法在感知阶段就规划好并行调用

**状态信息的注入方式也有问题**：`{intent_context}` 等占位符是运行时注入的动态数据，但 Prompt 把它们写成了结构规则，LLM 读的是"规则"而不是"当前现实"。

### JoyAI 的根本问题

**缺乏定量锚点导致执行不稳定**。"意图明确时直接执行"、"只有在确实无法继续执行时才澄清" 都是定性描述。当 LLM 处于模糊边界时，没有任何信号告诉它"当前信息够不够"，容易产生两种极端：要么过度追问（保守），要么在证据不足时就强行生成（激进）。

---

## 优化方案

核心思路：**状态信号是 LLM 的输入，不是 LLM 的替代品**。让量化信号成为 LLM 推理的"仪表盘"，而非把 LLM 锁死在一张决策流程图里。

### 改动一：重构状态区块的呈现方式

**原做法**：用标题+场景枚举的方式，把状态和行动绑定。
**新做法**：把状态块设计成"只读仪表盘"，明确标注每个字段的含义和判断建议，但不规定行动。

```markdown
## 当前状态仪表盘（只读，每轮执行前必须通读）

{state_block}

字段说明（辅助你判断，不是硬性规则）：
- intent_confidence: 意图识别把握度。低于 0.6 通常代表需要澄清；0.6–0.75 是灰色地带，结合 missing_slots 综合判断；高于 0.75 可放心执行。
- decision_confidence: 现有证据够不够做推荐。低于 0.7 说明还有关键信息缺口；高于 0.7 代表可以直接回复用户。
- information_gaps: 当前最薄弱的证据环节，按优先级排列。
- missing_slots: 意图已明确但还没收集到的关键参数。
```

这样 LLM 读的是"当前处境的描述"，而不是"必须走哪条分支"。

---

### 改动二：用推理原则替换决策树

**原做法**：场景 A/B/C/D/E 五路分支，每路对应固定行动。
**新做法**：三条推理原则 + 一个自检问题。

```markdown
## 执行原则

**原则一：先明方向，再动工具**
每轮开始前，先在心里完整读一遍状态仪表盘，明确"我现在知道什么、还缺什么、这一轮要交付什么"。这一步是思考，不是工具调用。

**原则二：证据优先，宁问勿猜**
在信息确实不足以做具体推荐时（感知到 decision_confidence 低 或 information_gaps 中有关键缺口），优先通过调用 SubAgent 补齐证据，而不是靠内置知识生成推荐。
- 若缺口来自用户侧（missing_slots 有关键槽位），且无法通过工具自行补全，才向用户追问，一次追问不超过 2 个问题。
- 若意图本身模糊（intent_confidence 明显偏低），先澄清意图，再收集证据。
- 严禁在证据不足时强行生成推荐。

**原则三：并行规划，最小步骤**
一旦确定要调用哪些 SubAgent，立刻判断它们之间是否有依赖关系。无依赖的缺口，必须在同一轮并行发出调用，不要逐轮串行。

**每轮执行前自检（Mental Check）**：
> "如果现在直接生成推荐，我是在调用真实证据，还是在凭空推断？"
> 如果答案是后者，必须先补证据。
```

---

### 改动三：SubAgent 描述从模板改为目标导向

**原做法**：强制规定 `description` 字段的格式（【任务目标】【用户原始Query】【已有上下文】【输出格式要求】）。
**新做法**：说清楚每个 SubAgent 的能力边界，让 LLM 自己组织描述，只规定输出约定。

```markdown
## SubAgent 能力边界

| SubAgent | 职责 | 不能做 |
|---|---|---|
| researcher | 实时搜索商品、价格、库存、趋势 | 不做对比分析，不评价好坏 |
| analyst | 基于 researcher 已返回的数据做横向对比、优劣分析 | 不自己搜商品，必须有数据才能调用 |
| critic | 评估售后政策、正品风险、投诉记录 | 不推荐商品 |
| memory_manager | 读取/写入用户长期偏好画像 | 不搜商品，不分析数据 |

**调用时的唯一格式约定**：在 description 中清楚说明"你要解决的具体问题"和"已有哪些上下文可用"。输出必须是包含 `evidence_type`、`data`、`summary` 三个字段的 JSON。
```

这样 LLM 在 description 里写的是真正的任务目标，而不是填空。

---

### 改动四：补充 JoyAI 的输出规范

BASE_PROMPT 的回复规范太简陋。直接采纳 JoyAI 的详细排版规则，包括：

- 首段纯文本、禁用 Markdown 标题开头
- 三级标题分组（严禁加粗标题）
- 禁用超链接、斜体、分隔线
- 商品卡紧跟商品介绍，不集中出卡
- 禁止暴露执行痕迹（"搜索"、"工具调用"等词汇）
- 人设：可靠伙伴，不是机械客服

同时保留 BASE_PROMPT 特有的 **禁止在 decision_confidence < 0.7 时生成推荐** 这一定量约束，作为硬红线写入回复规范区块。

---

### 改动五：意图澄清策略精细化

BASE_PROMPT 对澄清的处理只有"列出可能意图让用户选"。JoyAI 有"主动免确认"原则但没有澄清策略。两者合并：

```markdown
## 澄清策略

**能不问就不问**：意图明确时直接执行，规格不全时按"最优/畅销"默认补全并在回复中说明。

**必须澄清的情形**：
1. 意图有根本性分歧（如"帮我看一下"可能是推荐或查订单），无法安全默认
2. missing_slots 中存在无法通过工具或合理默认值补全的关键槽位

**澄清的执行要求**：
- 一次最多提 2 个问题，优先提供选项而非开放式追问
- 严禁在已知信息上重复追问
- 澄清后，系统将更新对应槽位，直接进入下一轮执行，不重新走意图识别
```

---

### 整合后的结构对比

| 维度 | 原 BASE_PROMPT | 原 JoyAI | 优化后 |
|---|---|---|---|
| 决策方式 | 硬分支决策树 | 纯 LLM 判断 | LLM 推理 + 量化信号辅助 |
| 状态使用 | 分支触发条件 | 无状态 | 只读仪表盘，辅助推理 |
| SubAgent 调度 | 缺口→Agent 查找表 | 无 | 能力边界描述，LLM 自主选择 |
| 并行调用 | 明确规定 | 全局规划建议 | 两者合并，并行为默认优先 |
| 澄清策略 | 意图不明 → 必须澄清 | 无法执行时才澄清 | 能默认则默认，无法默认才澄清 |
| 输出规范 | 简略 | 详细 | 采纳 JoyAI 详细规范 + BASE_PROMPT 定量红线 |
| 执行约束 | 步骤顺序约束 | done 工具约束 | 原则约束 + Mental Check |

---

这个方案的核心哲学是：**把 LLM 从状态机升级回推理引擎，用量化信号做罗盘，不做锁链**。状态信息告诉模型"现在在哪"，能力边界告诉模型"工具能做什么"，推理原则告诉模型"怎么思考"——具体走哪条路，由 LLM 自己决定。
