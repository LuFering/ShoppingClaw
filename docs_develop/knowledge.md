## 对这份文档的客观评价

整体框架是对的，三个判断标准（会出事故、企业独有、基本不变）逻辑清晰，五类知识分类也基本准确。但有几处值得商榷。

**过度简化的地方**：把所有知识都存成 JSON 是示意图写法，实际落地完全不够用。JSON 适合结构完全固定的规则，但"品类决策标准"、"经验结论"这类知识天然是非结构化的，强行 JSON 化会丢失大量语义信息，也让后续的语义检索变得很差。

**第四类"经验结论"的定性有问题**：文档说"让 LLM 生成一次然后固化"——这个建议风险很高。LLM 生成的经验结论本质上还是模型的参数知识，不是平台自己的运营沉淀。真正有价值的经验结论应该来自平台的真实交易数据和用户反馈，而不是 LLM 的一次输出。固化 LLM 的输出等于把幻觉变成了事实存入知识库。

**第五类 FAQ 的定位偏低**：文档把它描述为"简单但实用"，实际上结构化 FAQ 是知识库里维护成本最低、准确率最高、最容易做到精准检索的部分，应该是第一优先级来建，不是最后。

## 权重打分是否是企业主流

**不是**，至少不是主流的直接落地形态。原因有三个。

第一，权重是静态的，但用户决策是动态的。同一个用户在不同时刻问"学生党手机推荐"，背景可能完全不同——临近期末考试压力大倾向于快速决策，还是寒假有充足时间对比研究。静态权重无法感知这种微妙差异。

第二，权重数字本身很难维护。`"price": 0.4, "performance": 0.3` 这些数字谁来定、怎么验证合理性、多久更新一次，在工程上都是问题。实际企业里这些数字往往是拍出来的，缺乏可靠依据，时间长了就成了没人敢动的"祖传参数"。

第三，权重打分本质上是在用规则模拟判断，而 Analyst 本身是一个具备推理能力的 LLM。在你的架构里，Analyst 应该根据用户场景**自主判断**维度优先级，而不是查表套权重——这才是 SubAgent 作为专家存在的意义，也是上次讨论里我们确定的设计方向。

**企业实际主流做法是什么**：不存权重，而是存**决策框架**——告诉 Agent "在这个品类、这个场景下，应该重点关注哪些维度、为什么、有哪些已知陷阱"，让 LLM 在这个框架内自主推理，而不是执行一个打分公式。

## 五类知识的存储方式分析

### 第一类：平台规则与政策

**适合的存储方式：结构化数据库 + 精确匹配检索**

这类知识有唯一正确答案，不需要语义理解，需要的是精确命中。用向量检索反而会引入不确定性——"7天无理由退换"被检索成"可以退货"是正确的，但"未激活"这个关键条件可能在语义相近的情况下被忽略，造成事故。

正确做法是按品类、按场景建立结构化索引，精确匹配查询，查到什么就是什么，不经过任何语义模糊化处理。更新时走严格的版本管理，每条规则有生效时间和失效时间。

---

### 第二类：品类决策标准

**适合的存储方式：结构化文档 + 语义检索**

不是 JSON 权重表，而是自然语言描述的决策框架文档。比如：

```
【手机-学生场景】
核心关注：价格是硬约束，性能够用即可，续航在宿舍场景比性能更重要。
常见误区：被处理器型号误导，忽视实际日常使用流畅度。
场景特殊性：学生通常有换机周期考虑，二手保值率值得提及。
已知陷阱：部分主打"学生机"的产品在摄像头上偷工减料。
```

这类文档用向量检索，Analyst 拿到的是可以直接理解的判断依据，而不是需要解释的数字。

---

### 第三类：风控知识

**适合的存储方式：双轨制——规则引擎 + 向量检索**

风控知识本身分两种性质，需要分开存：

确定性风险（黑名单、已知假货品类）用规则引擎精确匹配，命中即触发，不走语义模糊检索，因为这类知识容不得"差不多"。

经验性风险（高退货率特征、常见坑点描述）用向量存储，让 Critic 在推理时召回相关的风险模式作为参考依据，标注"基于历史数据"而非确定性结论。

两者混在一起是危险的——用语义检索处理黑名单会漏掉精确匹配，用规则引擎处理经验模式又过于僵硬。

---

### 第四类：经验结论

**适合的存储方式：向量数据库，但来源必须是真实数据**

存储形式本身用向量检索是对的，因为这类知识本质上是非结构化的语义内容。问题在于内容来源。

正确的生产方式是从平台真实数据中挖掘：高分评价里的高频正向词汇、差评里的高频负向词汇、退货原因的分类统计。这些经过数据验证的结论才值得固化进知识库。用 LLM 直接生成然后固化，等于把模型偏见变成了系统事实，这在企业里是会出生产事故的。

---

### 第五类：高频问答

**适合的存储方式：FAQ 数据库 + 精确匹配优先、语义检索兜底**

FAQ 的检索策略应该是两层的：先做精确匹配（问题字符串相似度），命中则直接返回答案，完全不经过 LLM；精确匹配失败再走语义检索找最近似的 FAQ 条目。

这类知识的核心价值恰恰在于**跳过推理**——如果每次都走向量检索再让 LLM 综合，既浪费延迟，又引入了 LLM 对确定性答案进行"创造性解读"的风险。

---

## 一张汇总表

| 知识类型 | 存储形式 | 检索方式 | 核心原则 |
|---|---|---|---|
| 平台规则政策 | 结构化数据库 | 精确匹配 | 不允许语义模糊 |
| 品类决策标准 | 自然语言文档 | 向量语义检索 | 存框架不存权重 |
| 风控知识 | 双轨：规则库+向量库 | 黑名单精确匹配，模式语义检索 | 确定性和经验性分开 |
| 经验结论 | 向量数据库 | 语义检索 | 来源必须是真实数据 |
| 高频问答 | FAQ 数据库 | 精确优先，语义兜底 | 尽量跳过 LLM 推理 |
