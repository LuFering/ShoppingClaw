## 总体判断

方案的分层架构思路是对的，工程意识也有，但有几处设计决策在企业环境下会带来真实的麻烦。逐层分析。

---

## 可行的部分

**五层分层架构的逻辑是清晰的**，把精确匹配、语义检索、实时工具分开处理，这个方向在企业里是主流共识，没有问题。

**按 Markdown 标题分块**而非按字符数切分，这是正确的工程判断。"【手机-学生场景】"作为完整语义块入库，比被切成碎片的通用 chunking 效果好得多。这个细节说明作者有实际 RAG 踩坑经验。

**Metadata Filtering** 的引入也是对的。向量检索如果不加品类过滤，搜"学生手机推荐"可能召回"学生书包推荐"，相似度高但完全无用。

---

## 有问题的部分

### 问题一：hybrid_retriever 的意图路由设计过于乐观

文档里写的路由逻辑：
```
"怎么退款" → L1 FAQ
"学生买什么手机" → L3 向量
"某品牌是否假货" → L2 规则
```

这三个例子是刻意选的边界清晰的案例。真实用户的 Query 不长这样。

"这个耳机买了后悔吗" 应该走哪层？"华强北的 AirPods 靠谱吗" 是 FAQ 还是风控规则？"我想买个不踩雷的手机" 同时需要经验结论和决策标准。

用规则判断意图来路由，本质上是在用 if-else 解决一个语义问题，这在企业里是已经被验证走不通的路。**实际落地的做法是并联召回**——同时查多个层，各自返回结果，再做 Rerank 或让 LLM 综合判断用哪个。这比串行路由更鲁棒，也更容易维护。

---

### 问题二：rule_store 用 SQL LIKE 检索是个隐患

```sql
SELECT content FROM rules WHERE keyword LIKE '%退货%'
```

这个查询在规则库还小的时候没问题，但有两个企业场景下必然会遇到的坑：

**第一，关键词歧义**。用户说"这个东西能换吗"——没有"退货"这个词，LIKE 匹配失败，但语义上完全是退换货场景。纯关键词匹配的精确检索，对用语多样性的覆盖很弱。

**第二，规则内容本身不是一条 SQL 行**。"退换货规则"在现实里是一段有条件分支的复杂文本（7天/15天/品类例外/激活状态……），存成一个 `content` 字段，查出来直接给 Agent 用，Agent 面对的是非结构化的长文本，推理负担并没有减轻。

企业里的做法通常是：规则用结构化字段存（`trigger_condition`, `applicable_category`, `time_limit`, `exception`），查询时精确匹配条件字段，返回的是结构化结果而不是自由文本。

---

### 问题三：FAQ 的 Levenshtein 距离在中文场景下效果差

方案里写"失败后计算 Levenshtein 距离找最相似的问法"，这在英文 FAQ 里是常见做法，但中文的编辑距离对语义相似性的表达力很弱。

"保修多久"和"质保几年"——编辑距离很大，但语义完全相同。
"iPhone 保修多久"和"iPhone 屏幕修多少钱"——编辑距离很小，但语义毫不相关。

**中文 FAQ 的正确做法**：精确匹配失败后，走小型 embedding 模型做语义相似度，而不是字符串编辑距离。成本并不高，一个轻量级的 sentence-transformers 模型足够。

---

### 问题四：KnowledgeItem 的 confidence 字段定义模糊

文档提到要给知识条目加 `confidence` 置信度字段，"让 Analyst 知道拿到的是铁律还是参考建议"，方向是对的，但没有说这个值怎么来。

如果是人工标注——维护成本很高，一旦规则更新，所有相关条目的置信度都要重新评估。
如果是模型生成——谁来为这个数字的准确性背书？

企业里更实用的做法是**用来源类型替代置信度数字**：`source_type: "official_policy"` 就是铁律，`source_type: "operation_experience"` 就是参考。来源类型是确定的，不需要评分，Agent 在 Prompt 里知道不同来源类型意味着什么可信程度。

---

### 问题五：第三阶段的"统一调度器"被低估了

TODOLIST 把 `hybrid_retriever.py` 列为第三阶段，但这实际上是整个系统最复杂的部分，不是一个阶段末尾的收尾工作。

它需要解决：多层结果如何合并、冲突结果如何处理（FAQ 说能退货，规则库说不能退）、召回结果的排序依据是什么。这些问题每一个在工程上都需要独立设计，不是"实现路由"几个字能概括的。

建议把调度器提到第一阶段先做接口定义，哪怕初版只是透传，后续各层存储都围绕这个接口建，而不是最后才来对齐。

---

## 一个没提到但很重要的问题：知识库的写入侧

整份方案几乎全在讲"怎么查"，对"怎么写入、怎么维护、怎么更新"基本没有设计。

这在企业里是知识库失败的最常见原因。平台规则会修改，风控黑名单需要持续更新，经验结论要随着真实用户数据迭代——如果没有配套的写入流程和版本管理，三个月后知识库就会变成一个没人信任的数据垃圾堆。

至少需要补充：规则更新的触发机制、旧版本的失效处理、向量库内容的增量更新策略（ChromaDB 的 upsert vs delete+insert 在不同场景下行为不同）。

## 综合评分

| 维度 | 评价 |
|---|---|
| 分层架构思路 | 正确，可以沿用 |
| 存储技术选型 | ChromaDB + SQLite 组合合理，适合中小规模 |
| 检索策略设计 | 路由逻辑过于理想化，建议改并联召回 |
| 中文适配 | Levenshtein 不适合中文，需要换方案 |
| 写入侧设计 | 完全缺失，是最大风险点 |
| 实施路线图 | 调度器优先级排错，会导致返工 |

整体是一份有价值的设计草案，但距离企业可直接执行的落地方案还差写入侧设计、路由策略修正、中文适配这三块。可以作为起点，但不能直接照做。
