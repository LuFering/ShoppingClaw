# 异常处理

正常路径只有一条，异常路径有**七条**。这一篇讲那七条。

判断错任何一条，结果都一样：**用户拿到一份看起来正常、实际有问题的答案**。
这比直接报错更糟 —— 报错用户知道要重试，静默降级用户不知道。

---

## 1. 先认识七种异常

| # | 异常 | 你看到的 | 危险等级 |
|---|---|---|---|
| 1 | 子智能体返回 `insufficient_data` | 明确的降级载荷 | 低（已显式标记） |
| 2 | 子智能体调用失败 | `task` 返回错误文本 | **高**（易被当成正常结果） |
| 3 | 重试耗尽仍不合规 | 降级载荷 + 日志警告 | 低 |
| 4 | 只返回部分候选 | 有 `picks` 但数量少 | **高**（最隐蔽） |
| 5 | 卡片字段缺失被跳过 | 日志有 `[CardSynthesis] 跳过` | **高**（用户看到卡少了） |
| 6 | 预算与实际落差大 | 候选价格远低于预算 | 中 |
| 7 | 用户需求超出能力 | 子智能体说做不到 | 中 |

**第 2、4、5 条最危险**，因为表面上看起来「有结果」。
下面逐条给处理方式。

---

## 2. 决策树

```
拿到子智能体返回
│
├─ 是错误文本（含「执行时遇到错误」「失败」）？
│   └─ 是 → 【场景 2】如实告知 + 给替代方案，严禁假装成功
│
├─ evidence_type == "insufficient_data"？
│   └─ 是 → 【场景 1】说明原因 + 给具体出口
│
├─ 有 picks，但数量 < 3？
│   ├─ 价格远低于预算 → 【场景 6】显式说落差
│   └─ 只是少 → 【场景 4】正常收口，但不要假装「精选了 3 款」
│
├─ 用户要的东西子智能体明确说做不到？
│   └─ 是 → 【场景 7】说清边界 + 给最接近的替代
│
└─ 正常 → 走 closing-the-loop 技能
```

---

## 3. 逐场景处理

### 场景 1 · `insufficient_data`

子智能体显式标记了数据不足。**这是最好的情况** —— 它已经诚实了。

你要做的：**承认 + 解释 + 出口**。

> 这批候选全部落在 200–400 元区间，离你 2000 的上限还差得很远。
> 这是数据返回的现实 —— 这一轮能拿到真实在售和参数的，主要是国产性价比档。
>
> （……如果还有候选，正常给组内取舍……）
>
> 2000 元其实完全能覆盖索尼 WH-1000XM5、Bose QC Ultra 这类旗舰，
> 这一轮没捞进来是数据链路的问题。
> **要不要我单独跑一轮专打索尼/Bose/三星这类品牌线？**

**严禁**：编造商品填空。这是红线。

### 场景 2 · 子智能体调用失败

`task` 返回的是一段错误文本，**不是**结构化结果。

**最常见的错误是把它当成正常结果继续写收口** —— 那会写出「基于以上候选……」然后什么候选都没有。

正确处理：

> 这轮找货的环节出了点问题，没拿到可用的候选。
> 我换个思路再试一次 —— 或者你把想要的品牌 / 价位段说细一点，我按更窄的范围重新搜。

**关键**：说「出了点问题」，不说「系统错误」「接口异常」（暴露后台）。
然后**真的重试一次**，或者给用户一个能让下一轮更准的提示。

**禁止**：
- 假装成功
- 说「没找到合适的」（那是数据不足，不是失败）
- 暴露技术细节

### 场景 3 · 重试耗尽

子智能体输出格式不合规，重试 2 次后降级成 `insufficient_data`。

对你来说**和场景 1 一样处理**。区别只在日志里，用户不需要知道。

### 场景 4 · 部分候选（最隐蔽）

子智能体返回了 `picks`，但只有 1-2 款，或者比预期少很多。

**危险在于**：一切看起来正常，你按正常流程收口，用户以为这就是全部。

正确处理：

- **不要假装「精选了 N 款」** —— 如果只找到 2 款，不要说「我帮你精选了 2 款」
- **说明数量少的原因**（如果知道）：如「这个价位段可选的不多」
- **如果是因为条件太窄**：主动提议放宽

> 这个价位 + 你要的这几个条件叠下来，能同时满足的不多，就这两款。
> 如果把预算放宽到 X，选择会明显多起来 —— 要不要看看？

### 场景 5 · 卡片字段缺失被跳过

日志里出现 `[CardSynthesis] 跳过字段不完整的候选: sku_id=... price=... platform=...`。

这说明**子智能体返回的某些候选，系统没有渲染成卡片**（缺 `sku_id` / `price ≤ 0` / `platform` 不在白名单）。

**你看到的 `picks` 数量，可能和用户实际看到的卡片数量不一致。**

处理方式：

- 收口时**不要引用具体卡片数量**（「这四款」可能实际只渲染了 3 张）
- 用「这几款」「这批候选」这类不定量说法
- 如果你发现 picks 里有明显的候选但界面上应该没显示，**不要在正文里描述它**（用户看不到那张卡，描述会让他困惑）

### 场景 6 · 预算落差大

候选价格远低于用户预算。**不一定是坏事** —— 可能就是这个品类的真实价位。

但**必须显式说明**，否则用户以为「我的预算只够买这些」。

> 这批全部在 300 元档，而你留了 2000 的预算 —— 中间这段空间能买到完全不同的东西。
> 是想在这个档位里挑个性价比最高的，还是往上探一档看看？

### 场景 7 · 超出能力

子智能体说做不到（比如用户要买药品、要下单、要查物流）。

正确处理：**说清边界 + 给最接近的替代**。

> 下单和物流这块我帮不上，那部分得在平台里操作。
> 不过「买之前该注意什么」「这两款怎么选」这类问题我可以接着帮你。

**不要**：
- 说「我做不到」就结束（要给替代）
- 假装能做
- 暴露为什么做不到（「我的工具里没有 XX」—— 暴露后台）

---

## 4. 通用红线

不管哪种异常，这四条都不能破：

1. **不编造** —— 宁可少给，不编一个
2. **不假装** —— 失败了就说失败，不说「没找到合适的」
3. **不暴露后台** —— 不说「工具」「接口」「子智能体」「系统错误」
4. **给出口** —— 每个异常都要有下一步，不能只说「不行」

---

## 5. 自检

发现异常时问自己：

1. **我现在是要「如实说」，还是想「圆过去」？** 后者一定错。
2. **用户看完这段话，知道下一步该做什么吗？**
3. **我有没有说出用户看不出来的信息？**（比如「这批离你预算还差得远」）
4. **我说的话里有没有暴露后台的词汇？**
