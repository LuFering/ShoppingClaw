# 派遣类错误

> 数据来源：40 段真实生产对话（2026-10 导出）的工具调用统计。

---

## 基线数据

| 工具 | 调用次数 | 说明 |
|---|---|---|
| `task` | 64 | 派遣动作 |
| `orchestrate` | 28 | 编排卡合成（非模型调用） |
| `query_orchestration_sop` | 10 | 编排方法论检索 |
| `find_archive` | 8 | 查历史档案 |
| `list_subagents` | 4 | 查可派遣清单 |

| 子智能体 | 次数 |
|---|---|
| `pre_purchase` | 23 |
| `post_purchase` | **3** |

**`post_purchase` 只占 11.5%**。它的职责（归档 / 提醒 / 复盘 / 盯价）是「买之后」的动作，
而语料里大多数对话停在「推荐完」就结束了。

---

## 错误 1 · 口头归档（最隐蔽）

**表现**：正文里说「我把这个决策记到购物档案里了」，但**没有真的调** `save_to_archive`。

**证据**：语料里有 6 段对话提到了「档案 / 记下 / 归档」，
但 `save_to_archive` 全语料只被调用了 **2 次**。

**为什么危险**：

用户下次问「我上次选的那个」时，才发现档案是空的。
而且**当时没人发现** —— 用户以为记了，模型以为说了，日志里没有报错。

这是**静默的谎言**，比直接报错更糟。

**怎么改**：

- 说了要记 → **真的调 `task(post_purchase)`**
- 如果因为某种原因没调成功 → **不要说记了**

**自检**：我说「记下了」的时候，这一轮里真的出现过 `task` 调用吗？

## 错误 2 · 决策后继续推荐

**表现**：用户说「就红米 note14 吧」，模型继续介绍别的机型，或者再推一轮。

**真实案例**：

```
用户：就红米note14吧
模型：这个选择挺稳的，官方旗舰店 1169，售后和正品都有兜底。
      我把这个决策记到你的购物档案里，方便后续跟进价格和收货。
      下单前留意两点：结算页确认补贴价是否真的扣下来、认准"小米官方旗舰店"字样别走第三方店。
```

**这个案例是好的** —— 停止推荐、确认判断、说清归档、给实用提醒。

**反例长什么样**：

```
用户：就红米note14吧
模型：红米 note14 确实不错，不过同价位还有 XX 和 YY 也值得看看……
```

用户已经决定了，再推就是打扰。

**判据**：「就 X 吧」「选 X」「买 X」= 决策信号，不是「帮我再想想」。

## 错误 3 · 重复派遣

**表现**：同一批对象、同一类信息，派了两轮。

**用户视角**：进度条转两圈，等 60 秒，拿到的还是刚才那批东西。

**判据**（派遣前必问）：

> 我这一轮要派的活，和已经派过、或已经返回的，是不是同一批对象、同一类信息？

**特别注意**：用户追问上一轮的结果时（「刚才那第一款多少钱」），
**那个价格你手上已经有了**。重新派一轮是最典型的浪费。

---

## 错误 4 · 用串行拆闭环

**表现**：把「搜货」和「分析」拆成两次 `task` 调用。

**为什么错**：购前助手**内部**已经是完整闭环
（搜货 → 整理规格 → 筛硬约束 → 取舍 → 提示风险）。
拆开派的结果是：多一轮 30 秒以上的往返，而信息量不增加。

**正确用法**：串行只用于「不同任务确有依赖」，比如
「先归档，再根据归档结果决定要不要建盯价任务」。

---

## 错误 5 · 该查档案不查

**表现**：用户说「我之前记过 XX」，模型不调 `find_archive` 直接搜。

**为什么错**：用户主动提「记过」，就是在给信号 —— **用起来**。
不查的话，这次的结果可能和上次冲突，用户会觉得「你根本没记住」。

**正确动作**：

1. 先 `find_archive` 确认有没有记录
2. 再按新条件派 `pre_purchase`
3. 归档时**更新**原记录，不是新建

---

## 错误 6 · 简报信息不足

**表现**：`task` 的 `description` 只有一句话，比如「帮我挑个耳机」。

**后果**：子智能体看不到对话历史，只能按大众方向搜。

**必须包含**：对象（买什么/送给谁）、约束（预算/硬性排除）、场景（用在什么情况下）。

**详见**：`closing-the-loop` 技能里没有，这块内容在主提示词的派遣规范里。

---

## 错误 7 · 该派购后不派

**表现**：用户说「降价了告诉我」，模型口头答应但不派 `post_purchase`。

**为什么错**：`post_purchase` 持有 `create_monitor_task` 工具。
不派它，盯价任务就建不起来 —— 用户以为设好了，实际什么都没有。

**信号清单**（出现任一必须派）：

- 明确决策（「就 X 吧」）
- 说在用某件东西
- 要盯价 / 要提醒
- 要复盘

---

## 附：派遣前五问

1. 我要派的活，和已派过/已返回的，是不是同一批对象同一类信息？
2. 用户说了「就 X 吧」这类决策信号吗？说了 → 派购后归档，别再推
3. 我说了要「记下来」吗？说了 → 真的调工具
4. 简报里有没有对象、约束、场景？
5. 我是不是在用串行拆同一个闭环？
