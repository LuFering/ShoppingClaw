# 读收礼人

这一步的产出是**中栏那张人物档案卡**，它是整份礼物的地基。
地基错了，后面全废 —— 所以这一步的第一原则是**宁可标「待确认」，不要标「已确认」**。

---

## 1. 只取相关的

档案里可能有几十个字段，但本次送礼只关心四类：

| 取 | 不取 |
|---|---|
| 与收礼人的**关系**（母亲 / 同事 / 恋人） | 用户自己的购物车 |
| **明确表达过**的喜好 | 推断出来的泛化标签 |
| **明确禁忌 / 过敏 / 不收** | 与送礼无关的消费记录 |
| 与本次**场合**相关的历史 | 全部历史订单 |

多取的代价不是噪音，是**污染** —— 拿一条无关记录当依据，
会得出一个「有依据但错」的结论，比没依据更危险。

---

## 2. 三态怎么定（前端硬要求）

| state | 什么时候用 | 界面表现 |
|---|---|---|
| `confirmed` | 来自档案记录，或用户本次明确说了 | 实心点 |
| `inferred` | 由上下文推出，**但无直接依据** | 空心圈 + 标「推测」 |
| `pending` | 需要用户点头才能用 | 灰虚线圈 + 「待确认」 |

**判据只有一条：能不能指出来源。**
指不出来源就是 `inferred`；用户没确认过就是 `pending`。

**最容易犯的错**：为了让档案卡看起来丰满，把推测标成 confirmed。
这是 `.impeccable.md` 明令禁止的「黑箱」——界面好看了，但用户照着买了错的东西。

---

## 3. 读不到时怎么办

**如实说「没有」，并告诉用户补哪一句最有用。**

不要：
- 用「一般妈妈都喜欢…」这类常识填位
- 把 `life`（生活状态）这类档案里根本没有的组标成 confirmed

要：
- 标 `pending`，note 里写「（档案里没有这类记录）」
- 在「当前理解」里说明「我手上还没有可用的偏好记录」

---

## 4. 禁忌单独处理

禁忌是**唯一不能靠推断**的一类：
- 只有档案里明确记过（如曾把某类商品标为 dropped），或用户这次说了，才能写
- 写的时候标 `danger`，前端会用危险色单独分区
- 宁可问一句「有需要避开的吗」，也不要猜

**过敏**这类尤其致命：编错一个，礼物就变成伤害。
