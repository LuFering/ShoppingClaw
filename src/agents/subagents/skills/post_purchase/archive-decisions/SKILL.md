# 决策归档

用户说「我决定买 X 了」「帮我记一下」「盯一下价格」的时候，你做的是：
**把这一轮对话变成一条明年还能用的记录。**

档案的质量不在"记没记"，在**记得对不对、写得能不能复用、后续跟没跟上**。

---

## 一、先判状态（最常错的一步）

| 用户说的话 | 状态 | phase |
|---|---|---|
| 「想买 / 看看 / 帮我挑」（还没定） | 需求 | `need` |
| 「在对比 A 和 B」「还在挑」 | 候选 | `candidate` |
| 「就买这个了 / 决定了 / 已下单」 | 已决策 | `decided` |
| 「已经用了 / 用了半年」 | 使用中 | `using` |
| 「不要了 / 算了 / 放弃了」 | 放弃 | `dropped` |

**「我决定买 X 了」就是 `decided`，不是 `candidate`。**
实测出现过把"已决策"记成"候选"的口径——下轮用户看到"你还在挑"会觉得你没听懂。

---

## 二、一条好记录长什么样

字段能拿到几个填几个；**拿不到的留空，不要编**：

- **target**：买的东西（具体到型号）
- **budget**：预算上限（用户说过的那个数）
- **scenario**：用在哪（通勤 / 办公 / 生日）
- **for_whom**：给谁（自己 / 妈妈 / 同事）
- **note**：一句话说清「用户为什么选它」——这是下轮复用的核心
- **risk**：下单前要确认的坑（有才写）
- **thread_id**：关联本轮会话，方便从档案跳回对话

**note 的判据：下个月用户问「我上次为什么选的这个」，这句话能不能答上来？**

- ✅ 「已决策购买华为 MateBook D16：16 英寸大屏适合办公多窗口，预算上限 6000」
- ❌ 「用户想买笔记本」（等于没记）

---

## 三、更新还是新建？

先查当前档案状态，再决定：

- **同一件商品的后续进展**（预算调整、重新挑、换档位）→ **更新原记录**，不新建
  （实测：用户「预算从 800 提到 1500，重新挑几款」——应该更新原条目）
- **盯价 / 提醒** → 挂到**既有记录**上（`set_reminder` 到 record_id），不新建重复条目
  （实测佳例：已有对应记录时，正确做法是「挂到 record_id=xxx，不新建」）
- **全新的需求** → 新建

重复条目是档案的慢性病：用户下次问"我的耳机记到哪了"，翻出三条。

---

## 四、跟进动作（该顺手做的，别留给用户想起来）

归档之后往往还有"下一步"：

- **决策已定** → 顺手挂下阶段提醒：「到货后一周提醒你看是否保价」这类，一句话说清
- **用户要盯价** → `create_monitor_task`。两个动作：
  - **先查重复**：已有相同监控就不再新建（实测佳例：发现已有 4 条相同监控，如实说明"已经在生效"，不再重复挂）
  - **顺手看现价**：如果现价已经低于目标价，直接告诉用户——「这条线现在已经破了，不用等」（实测佳例）
- **买了用了一段时间** → 引导复盘（`write_review`），素材是她自己的使用感受

---

## 五、说话的分寸（对用户）

- **别半截话**：说了"我帮你看看 XX"就真去查；查不了就说查不了。
  实测反例：回复停在「我把这款记进档案，顺便看看配置」，然后没有下文——用户不知道到底记没记
- **说到做到**：说「已记入档案」之前，`save_to_archive` 必须已经调用成功。
  嘴上说记、实际没记，是最隐蔽的失信
- **内部错误不上桌**：查档案遇到接口 / 字段报错，对用户说「档案这边暂时没翻出来」，不要说「user_id 类型错误」「报了个内部错误」这类技术细节
  （实测反例：把数据库报错原文暴露给了用户）
- **部分失败如实说**：如果只有一部分动作成功（如决策记下了、偏好落库失败），说清「记下的部分不影响后续使用」，不用展开技术细节，也不要假装全部成功

---

## 自检

1. 状态判定对不对？（「决定买」≠ 候选）
2. note 能不能回答「为什么选它」？
3. 该更新的记录，我是不是又新建了一条？
4. 说了要做的跟进（提醒 / 盯价），真的调工具了吗？
5. 我的回复有没有半截话、内部错误、或"回头再说"的空头支票？
