# 送礼智能体（`/proxy`）— 落地记录

> 用途：把「原状」与「现状」摊平，供后续接手。**本文只记录已经发生的事**。
> 现状全部来自代码实读 + 线上实测，出处标注在表里。
> 日期：2026-09-24

## 0. 一句话

`/proxy` 原本是**纯前端演示**：4 个视图共 5389 行，数据 100% 来自
`data/giftWorkbenchStream.js` 的模拟流与 `data/giftProfile.js` 的硬编码 TASK，
后端零实现（`src/agents/independent/gift/` 是个**空目录**，概念定了、代码没写）。
本轮把它做成**真跑图、真取数、真读档案**的独立 agent。

## 1. 与采购智能体（`/planning`）的关系

**并列，不是复用。** 共用**服务模式**，不共用业务逻辑：

| | 采购 `/planning` | 送礼 `/proxy` |
|---|---|---|
| 任务性质 | **决策收敛**：N 个候选 → 1 个方案 | **意义建构**：1 个意图 → 一段过程 → 1 份礼物 |
| 信息流向 | 横向汇聚 —— 必须并置才能比较优劣 | 单一对象生长 —— 必须「看得见改动」才成叙事 |
| 核心产物 | 决策图 | 人物档案 |
| 判据 | 参数可解释（价格、规格） | **心意可解释** —— 为什么是这几件 |
| 用户心态 | 我是管理员，我要高效比价 | 我是送礼者，我在倾注心意 |

依据见 `web-v2/.impeccable.md` 的「分区豁免」。设计上的直接后果：

- **表不合并**：`gift_runs` / `gift_events` 而不是复用 `planning_runs` / `planning_events`。
  共用会立刻需要「一半字段对另一半为空」的分支。
- **阶段划分不同**：采购是「筛选/对比」这类收敛动作，送礼没有 ——
  它是「读人 → 定主题 → 选构成 → 说清为什么」。

## 3. 事件契约（前端状态机不用改的原因）

后端 `gift_service.emit()` 的 kind 与前端 `useGiftWorkbench.apply()` 的 `ev.t`
**一一对应** —— 这是刻意的，接真后端时前端状态机的分支**一行没改**：

| kind | payload | 落点 |
|---|---|---|
| `stage` | `{key}` | 左栏：推进到哪一步 |
| `step` | `{key, status, evidence?, why?}` | 左栏：某步的状态与**关键依据** |
| `live` | `{key, text, more}` | 左栏：实时描述 |
| `excluded` | `{name, why}` | 左栏：被排除的候选（**保留理由，不删除**） |
| `profile` | `{key, state, text?, note?}` | 中栏：某组档案被写活 |
| `understanding` | `{text, from}` | 中栏：「当前理解」 |
| `deliverable` | `{key, state, data?}` | 右栏：交付物状态与内容 |
| `done` | `{}` | 收敛 |

## 4. 三条实测教训（都写进代码注释了）

### 4.1 关键词必须是**具体品类名词**

实测真实淘宝 MCP（2026-09-24）：

| 关键词 | 前 3 个结果 | |
|---|---|---|
| 「日常小家电」 | 服装、电钻工具套装 | ❌ 抽象词被拆开匹配 |
| 「家居 实用」 | 义乌小商品、毛绒玩具 | ❌ 组合词召回杂货 |
| 「护手霜」 | 植护 / 香氛 / roopy | ✅ |
| 「香薰」「保温杯」「按摩仪」「丝巾」 | 全是真品类 | ✅ |
| 「茶 礼盒」 | 绿茶礼盒 | ✅ |

入口页用户勾的「真的用得上 / 看得出花了心思 / 留下一个记忆」是**抽象标签**，
必须翻译成具体商品。`stages.SIGNAL_TO_GOODS` 做这件事，表里每条都实测过。

> ⚠️ 该表的键**同时收**入口页的说法（「真的用得上」）与简写（「实用」）——
> 两套说法都在用，漏收一套会**静默**退化成兜底关键词（搜出无关品类）。

### 4.2 不能按价格降序选件

试过。结果给「给妈妈的生日」选出 **¥336 的电钻工具套装**当主力
（它是候选里最贵的）。MCP 返回**本身按相关性排序**，比「最贵的」靠谱得多。

### 4.3 同一品类只能取一件

关键词含「保温杯」时，纯按相关性会连着挑 **3 个保温杯** ——
那不是礼盒，是同一样东西买三遍。

这条修了**三轮**才彻底，过程值得记：

1. 第一版：`combine` 里手写分组逻辑，但 `verify_candidates` 重建 dict 时
   **漏透传 `_kw`** → 分组键全成了「其他」→ 表现是「代码看着有分组、实际没有」
2. 第二版：修了透传，但检索截断用 `uniq[:N]` → 第一个关键词的 6 条占满，
   **第二个关键词整个被丢掉**
3. 第三版：把「按品类轮流取」抽成 `_round_robin_by_kw()`，检索截断与组合
   两处**共用一份**。重复实现正是前两个 bug 的来源。

## 6. 未做 / 已知问题

### 6.1 推理是「薄」的（本轮范围，非缺陷）

取数全真（淘宝 MCP、档案读取），但**取舍规则是占位的**：
- `combine` 按「品类轮流 + 检索相关性」选件，不做多维度评分
- `build_message` 按模板拼寄语，不调 LLM

升级入口明确：`stages.py` 里 `combine` 与 `build_message` 两个纯函数，
改它们即可，事件契约与前端都不用动。

### 6.2 「改一下」只标记，不重推

`POST /runs/{id}/revise` 把该组档案置为 `pending` 并记事件，
但**不会重新跑推演**（那需要 LLM 参与）。前端提示语已如实说明。

### 6.3 `GiftConciergeView.vue` 是孤儿

521 行，**无路由、无任何 import**。它的入口表单设计被
`GiftEntryView.vue` 吸收了一部分（送谁/场合/预算/在意点）。

**未处理**，因为不确定它是「待接的入口」还是「废弃的旧版」：
- 若废弃 → 应删
- 若要保留 → 应挂路由

需要产品决策。同理还有 `/proxy/box`（GiftBoxView，1063 行）与
`/proxy/scroll`（GiftStreamView）—— 路由注释说「保留便于对照」，
但它们各自的 mock 数据（`giftDemo.js`）仍在。

### 6.4 `data/giftProfile.js` 的 mock 内容成了死代码

`PLAN` / `COMPARE` / `BUDGET_ROWS` / `MESSAGE` / `SUPPLY` / `ORDER` /
`EXCLUDED` / `TASK` 这些导出**已不再被 workbench 消费**（内容现在来自后端），
但仍被 `giftWorkbenchStream.js`（模拟流，也无人消费）与
`GiftBoxView`/`GiftStreamView` 引用。

**未清理** —— 因为 §6.3 那些孤儿视图还在用，删了会白屏。
等孤儿视图的去留定了再一起清。

### 6.5 档案读取的依赖

`read_recipient_context` 调 `recall_past_decisions` + `get_user_shopping_context`。
这两个工具走 `bind_user_id` 注入 user_id（与购后助手同机制）。

实测该用户（id=2）有档案数据，但**没有与「妈妈」相关的送礼历史**，
所以中栏的「已知喜好」「明确禁忌」都标了 `pending` —— 这是**正确行为**
（不编造档案），不是 bug。要看到 confirmed 状态需要先有送礼记录。
