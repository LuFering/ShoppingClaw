### 最关键的一条工程判断

**做法是「加翻译层」，不是「发明新协议」。**

这直接决定了实现路线 —— 采用**runtime 合成**（对照表 v2 的 §3.1 方式 B）：

> 不改 LLM、不注册假工具、不加 LLM 往返，而是在 runtime 侧把**已经发生的执行事实**翻译成契约形态。

好处：零 LLM 成本、渐进节奏完全可控，且 `orchestrate` / `task` 这两个「registry 里根本不存在」的编排动作自然有了出处。

### 第 3 发完整战绩

```
orchestrate      7 事件 / 6 档渐进显形 / 同 tool_call_id / mid=round-1-s1
                 intent → skills → rag → mcp → dispatch → decision
task             2 事件，带 subagent_run（researcher，planned=3）
subagent_drill   2 事件，expand → collapse，slug=购前助手
气泡归属         编排类全 mid=round-1-s1，业务类 mid=lc_run--…
```

### 三轮实测暴露并修复的两个线上事故

**事故 1：`TOOL_TASK` 漏 import**
- 现象：`chat_stream_service.py:825` → `NameError: name 'TOOL_TASK' is not defined`，**整条 SSE 流被打断**
- 根因：import 块只引入了 `TOOL_ORCHESTRATE`，漏了 `TOOL_TASK`
- 教训：契约里三个编排工具名（`orchestrate` / `task` / `ask_user`）必须**全部**引进来，缺一个就是线上事故

**事故 2：气泡归属错，编排卡被劈成两个气泡**
- 现象：`orchestrate` 用 `round-1-s1`，紧随的 `task` 却用 LLM 的 `lc_run--01a0b29f-…` → 前端分到两个气泡
- 根因：工具事件的 `message_id` 一律取 `getattr(msg, "id")`
- 修法：`_ORCH_OWNED_TOOLS = {orchestrate, task}` → 统一挂 `orchestrator.bubble()`；
  业务工具（`search_products` 等）仍挂 LLM run id，形成「正文→工具」自然节奏
- 这是项目里**第 4 次**踩 `message_id` 坑

**事故 3（同源）：`subagent_run.call_id` 必须 rebind**
- 合成 id 与 langchain 真实 `tool_call_id` 不一致 → 前端按 id 匹配不上卡片
- 修法：新增 `rebind_task_call_id()`
