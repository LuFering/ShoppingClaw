## 二、当前构造的问题（按严重度排序）

### P1　`system_prompt` 与技能大面积重复，渐进披露被抵消一半 ★最严重

- **现象**：§3 分析规范 ≈ `comparing-products` 正文；§4 风险审计规范 ≈ `screening-risks` 正文。
- **后果**：① 同一套方法论每轮都在 system prompt 里付一遍 token，`read_skill` 省上下文的设计被吃掉一大半；② 两处口径会各自演化 —— 现在就已经有缺口：prompt 写了"0-10 分"，但**没写技能里那条关键约束**"同一维度下所有候选必须用同一把尺子"；③ 冲突时没有优先级规则。
- **结论**：prompt 该瘦身，方法论下沉到技能，prompt 只留「角色 + 边界 + 路由 + 契约」。

### P2　输出契约是空的，主智能体出卡只能靠"再解析" ★结构性

- **现象**：`model/__init__.py` 空文件 → 子智能体返回自由文本；而主智能体的 `render_product_card(product: dict)` / `format_comparison_table(products: list[dict])` 需要结构化入参。
- **后果**：主智能体必须从自由文本里二次抽取字段 → **出卡丢字段 / 编字段**。前端卡片依赖真实 `sku_id` 与价格，这是红线。

### P3　工作流被拆成两处，且有方法论硬编码在 prompt 里

- **现象**：§2 定义固定 4 步；6 个技能各自又有「何时使用 / 操作步骤」。而检索策略（关键词数量、搜索次数上限、详情 SKU 上限、搜不到怎么办）**只存在于 prompt**，没有任何技能承载。
- **后果**：模型要同时遵守两套流程；改检索策略必须动 prompt 而不是技能（违反"prompt 少动、技能常迭代"的原则）。

### P4　没有「意图 → 技能」路由表

- **现象**：§6 只举例"可能串行读取"，没有确定性映射。
- **后果**：6 个技能全靠模型按 description 自由匹配，容易漏读 —— 尤其 `clarifying-needs` 这种最上游、最容易被跳过的（它没有工具做"硬提醒"）。

### P5　两个规格工具的 `display_name` 几乎同名，职责被混淆

- **现象**：
  - `get_products_specs_batch` → display_name **"批量获取商品规格（用于对比）"**，实为**联网按 sku_ids 拉取**；
  - `get_products_specs_extract` → display_name **"批量获取商品规格"**，实为**纯本地整形，不取数**。
  - 且 `get_products_specs_batch` 在整份 prompt 里**一次都没被提到**。
- **后果**：模型分不清"该拉数据"还是"该整数据"；`batch` 大概率被闲置或误用（明明本地就能整形，却去联网）。

### P6　购前 0 个脚本，但有两处确定性计算明显适合

- **现象**：`hunting-deals` 明确要求"券的可叠加性**不要断言**、写成待确认"，但叠加规则（平台券 × 店铺券 × 品类券 × 国补）本身是**规则化**的，可以枚举校验；`checking-compatibility` 第 5 步的整套到手价累加同理。目前购前没有任何技能声明 `run_skill_script` → 该工具在购前永远不可见。
- **后果**：到手价与叠加判断留在模型侧推理，误差与不可复现性都消不掉。

### P7　门控覆盖与技能分工不对齐

- **现象**：`price_calculator` / `query_risk_policy` 已门控；但 `query_category_knowledge`（品类评估标准）与 `filter_products_by_criteria`（硬条件剔除）的使用时机**完全由技能定义**，却常驻可见。
- **后果**：不算错，但门控价值被削弱；模型可能在没读技能时就用这些工具，产出不符合方法论口径。

### P8　模型档位与角色可能不匹配（待你确认）

- **现象**：购前用 `sensenova-6.8-flash-lite`（轻量档）。购前要做多维推理 + 风险分级 + 体验转译，是**重推理**角色；购后（读画像、写记录、日期计算）明显更轻。
- **后果**：可能是"让轻模型干重活"。是否分档（购前强、购后轻）需要你定。

## 三、预期构造

### 3.1 分层原则（一句话定分工）

| 层 | 负责 | 不负责 |
|---|---|---|
| `system_prompt` | 角色、边界纪律、**技能路由**、输出契约 | 任何方法论细节 |
| **Skill** | 方法论：怎么判断、怎么排雷、怎么搜 | 取数、精确计算 |
| **Tool** | 确定性动作：取数、筛选、算价 | 判断与取舍 |
| **Script**（技能内） | 精确计算：多券叠加、日期、批量算表 | 需要判断的部分 |
| 主智能体 | 出卡与交付 | 领域判断 |

### 3.2 期望的 `system_prompt` 骨架（目标 ≈ 55 行）

| 新段落 | 内容 | 相对当前 |
|---|---|---|
| ① 角色与价值 | 保持原文 | 不变 |
| ② **技能路由表** | 「输入形态 → 先读哪个技能 → 再读哪个」 | **新增**（当前缺，P4） |
| ③ 工具纪律 | 只写"哪些是主干、各自何时用"；**明确 `get_products_specs_batch`（联网拉取）与 `get_products_specs_extract`（本地整形）的分工** | **重写**（当前 §2 只提 extract，P5） |
| ④ 红线与边界 | 零幻觉、不越权、不跨域、及时收手、不伪造（合并当前 §1 红线 + §5） | 合并精简 |
| ⑤ **输出契约** | 固定结构化结论块（见 3.5） | **新增**（P2） |
| ⑥ 技能使用规范 | 保留（含 `references/` 与 `scripts/` 用法） | 精简，去掉与技能清单重复的部分 |

**删除**：当前 §3 分析规范、§4 风险审计规范 → 下沉进技能；§2 的检索策略 → 下沉进新技能。

### 3.3 期望的工具体系

|---|---|---|

| `get_product_full_detail` | 主干常驻 | — |

| `get_products_specs_extract` | 主干常驻 | prompt 里写明它是**本地整形** |
| `read_skill` | 常驻 | 激活入口，不可门控 |

### 3.4 期望的技能体系（6 → 7）

|---|---|---|
| `clarifying-needs` | 已有 | 微调：接收从 prompt 下沉的"硬约束必须落到可筛选字段" |
| **`searching-products`** | **新增** | 检索策略：关键词构造、并行搜索、搜索次数预算、**搜不到时的降级路径**（换词 / 放宽 / 转向替代品 / 反问用户）、结果去重与预筛 |

### 3.5 期望的输出契约（需你二选一）

**方案 A（推荐）——修活 JSON 协议**
- 在 `model/__init__.py` 导出 `PrePurchaseOutput`，字段覆盖出卡所需：候选列表（`sku_id` / `title` / `price` / `rating` / 维度分 / 风险级别）+ 结论 + 无推荐时的共性缺陷。
- 收益：主智能体拿字段直接出卡，**不再从自由文本猜**。代价：新增 schema + 回归测试。

**方案 B——固定文本结论块**
- prompt 里规定一个字段名固定的 markdown 结论块，主智能体按块解析。
- 收益：改动小。代价：仍是解析，且模型可能写歪。

### 3.6 期望的路由表（示例，落地时按此措辞）

| 用户输入形态 | 先读 | 再读 |
|---|---|---|
| "想买个……（场景 / 感觉）" | `clarifying-needs` | `searching-products` → `comparing-products` → `screening-risks` |
| 给了单个商品链接问"值不值" | `evaluating-fit` | `screening-risks` |
| 已有多于一个候选 | `comparing-products` | `screening-risks` |
| "贵不贵 / 什么时候买便宜" | `hunting-deals` | — |
| "要买一套 / 这两个能不能配" | `checking-compatibility` | `hunting-deals` |
| 正品存疑 / 价格异常低 | `screening-risks` | — |
| 下单前的最后确认 | `screening-risks` | `evaluating-fit` |

## 五、需要你定的决策点

1. **是否采纳「prompt 瘦身、方法论全部下沉技能」**（对应 P1 / P3）。这是本轮最大的一处结构改动，会动 `system_prompt` 整体骨架。
2. **是否新增 `searching-products` 技能**（承接现在硬编码在 prompt 里的检索策略）。
3. **是否为购前加脚本**（`stack_discounts.py` / `bundle_total.py`），并给对应技能声明 `run_skill_script`。
4. **输出契约走 A（修 JSON）还是 B（固定文本块）**。
5. **门控是否扩展到 `filter_products_by_criteria` 与 `query_category_knowledge`**（有"技能被跳过则工具消失"的风险，需要路由表兜底）。
6. **模型是否分档**（购前强 / 购后轻）。
