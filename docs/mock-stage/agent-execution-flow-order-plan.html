/agent 执行流时序优化方案

问题：为什么执行流是「工具 → 卡片 → 文本」？目标：正文①开场白 → 工具 → 文本 → 卡片 → 文本。前后端是否都要改？—— 结论见下。
一句话结论：这套时序的机制前后端都已经存在（后端 prompt 有硬性条款、SSE 桥按轮次 message_id 流式、前端已是 式时序分组）。 你看到的错误顺序，直接原因是我给你的 mock 场景就是按「工具→卡片→文本」写的——它不代表真实系统设计。 所以主要工作不是"造功能"，而是三件事：① 重写 mock 场景（立即）② 前端按清单验证 ③ 接真后端后验证模型的遵循度并强化。

1. 为什么你现在看到「工具 → 卡片 → 文本」

环节现状（已逐一查证）判定
mock 场景 测试指导文档 §4 的 runScenario 发事件顺序就是 thinking → 工具 → 卡片 → 正文；且没发 message_id，所有正文挤进同一条目 根因（mock 层面）
后端提示词 BASE_PROMPT.md:77/79："必须先产出正文①、再调用工具，不允许'先调工具、稍后再补正文'顺序"（最高优先级硬性条款）；:123："推荐具体资源必须紧跟对应 UI 卡片，严禁先集中介绍再统一出卡" 已有，且正是你要的
后端 SSE 桥 chat_stream_service.py：token 流按 message_id = msg.id 下发（每轮 LLM 一个 id）；tool_calls 带同一 message_id；render_product_card 落库前先 flush 已累积正文再存卡——注释原文即"按 正文→工具→正文 的顺序自然切段" 已有，为交错设计
前端渲染 AgentChatComponent.vue 的 conversationViews 已是 式分组：message / tool-group / 过程组按数组顺序渲染；卡片在 tool_complete 到达时作为独立条目追加到 conv.order（到达即位置） 已有，待验证
为什么"文→卡→文"天然成立：LLM 一轮里发出 正文+tool_calls 后本轮结束、工具才执行；工具结果回来后是新的一轮（新 message_id）。 所以「正文② → 卡片 → 正文③」天然是 round-2（文本+出卡工具调用）→ 工具执行（卡片到达）→ round-3（新文本）。 前端按到达顺序追加，顺序自然正确，不需要重排逻辑。

2. 是怎么做的（已查证，作为对标）

机制ShoppingClaw 对应
web/src/utils/messageGrouping.js → getConversationDisplayItems：消息数组按时间顺序遍历，AI 消息的 tool_calls 归组为 tool-group 插在原位置，正文独立 → 渲染顺序 = 真实到达顺序 conversationViews（AgentChatComponent 内）+ ToolCallsGroupComponent —— 同构，已移植
每轮 LLM 调用一个 message_id，正文与该轮 tool_calls 同 id 归组 → 「正文→工具→正文」自然切段 chat_stream_service.py make_chunk(message_id=msg.id) —— 已实现
顺序来自 agentic 循环本身：模型边说边调工具（第一轮就产出承接文本），不是前端摆出来的 BASE_PROMPT 正文①条款 —— 已写，待验证模型遵循度

3. 目标时序（验收基准）

正文① 开场白（逐 token 流式，点明接下来做什么）
→ 工具组 search_products（calling → completed，人类可读参数与结果摘要）
→ 正文② 推荐语（新一轮 message_id，逐 token）
→ 商品卡片 紧跟正文②（介绍到哪件，卡出到哪件）
→ 正文③ 收尾 / 追问（再一轮 message_id）
→ done
禁止：工具先于任何正文出现 ╱ 卡片集中在最后统一出 ╱ 全部正文挤成一条

4. 方案：三步走（对应你"一步步改造"）

第一步（现在就做）：重写 mock 场景

替换 agentStreamMock.js 里的 runScenario。关键修正：每轮事件带 message_id；正文①先行；卡片夹在两段文本之间。

// 修正版：正文① → 工具 → 正文② → 卡片 → 正文③ → done
async function runScenario(query, send, sleep, aborted) {
  const type = async (text, mid) => {
    for (let i = 0; i < text.length; i += 6) {
      send('message_chunk', { content: text.slice(i, i + 6), message_id: mid })
      await sleep(35)
      if (aborted()) return false
    }
    return true
  }

  // —— 1) 正文①：开场白（先说话，再调工具）——
  await type('好的，我来帮你给妈妈挑一份合适的生日礼物。先按「喝茶、看书」两个偏好找一批候选，再比价收敛。', 'round-1')

  // —— 2) 工具：搜索（同属 round-1 的 tool_calls）——
  send('tool_start', { tool_call_id: 'call_search_1', tool_name: 'search_products',
    arguments: { keyword: '茶 茶具 书', budget: 800 },
    meta: { icon: 'Search', category: '检索' }, message_id: 'round-1' })
  await sleep(1200)
  send('tool_complete', { tool_call_id: 'call_search_1', tool_name: 'search_products',
    duration_ms: 1200, result_preview: '找到 12 件候选：茶具 5 / 茶叶 4 / 书 3', message_id: 'round-1' })

  // —— 3) 正文②：推荐语（新一轮）——
  await type('结合她的偏好，我最推荐这套「茶香组合」：一盒武夷岩茶配一只手工紫砂茶杯，天天用得上。', 'round-2')

  // —— 4) 卡片紧跟正文②（严禁集中出卡）——
  send('tool_start', { tool_call_id: 'call_card_1', tool_name: 'render_product_card',
    arguments: { items: ['武夷岩茶', '紫砂茶杯'] },
    meta: { icon: 'Package', category: '呈现' }, message_id: 'round-2' })
  await sleep(900)
  send('tool_complete', { tool_call_id: 'call_card_1', tool_name: 'render_product_card',
    duration_ms: 900, message_id: 'round-2',
    result_content: JSON.stringify({ type: 'product_card', data: {
      title: '妈妈生日礼 · 茶香组合',
      items: [
        { name: '武夷岩茶 礼盒装', price: 268, shop: '张记茶行', tag: '茶叶' },
        { name: '手工紫砂茶杯', price: 199, shop: '宜兴窑', tag: '茶具' }
      ]
    } }) })

  // —— 5) 正文③：收尾（再一轮）——
  await type('如果还想加一本散文集，整体仍控制在 600 内。需要我生成可下单清单吗？', 'round-3')

  // —— 6) done ——
  send('done', { statistics: { total_tokens: 1280, elapsed_ms: 5200 } })
}
为什么必须带 message_id：前端靠它把「该轮正文 + 该轮工具」归为同一条消息、不同轮切开。 旧 mock 不带 id，全部正文挤进同一条目——即使顺序发对，渲染也会变成"一整段文字 + 卡片悬在后头"。 这是旧场景除顺序外的第二个错误。

第二步：mock 阶段的前端验证清单

  1. 正文①先行：开场白逐 token 出现，先于任何工具卡片。
  2. 工具组位置：search_products 的工具组出现在正文①之后（同轮归组），状态 calling→completed。
  3. 卡片位置：商品卡出现在正文②之后、正文③之前——「介绍到哪件，卡出到哪件」。
  4. 轮次切段：三段正文是三条独立气泡（message_id 不同），不是连成一大段。
  5. 历史一致：done 后刷新页面，历史里的顺序与实时一致（后端 flush 逻辑保证；mock 阶段先验证实时）。
  6. 异常路径：在卡片前发 error、或中途点停止——已出内容不重排、不重复。
  7. 变体场景：再写一个「多商品逐段出卡」场景（正文②₁→卡①→正文②₂→卡②→正文③），验证连续交错。

第三步：接真后端后的验证与强化（机制已在，验的是"模型听不听话"）

  1. 正文①遵循度：BASE_PROMPT:79 已是最高优先级硬性条款，但条款 ≠ 模型行为。跑 10 个真实问题统计：首轮 tool_call 之前有没有正文①。违规率高 → 在 graph 里加兜底（检测到"首轮即 tool_call 且无正文"时注入纠偏提示重试一次），而不是继续加长 prompt。
  2. 出卡时机：BASE_PROMPT:123 已禁止集中出卡。若模型仍"先集中介绍再统一出卡" → 给 render_product_card 加结构性约束（每次只渲染一批、参数要求紧跟对应推荐段），或在 SubAgent 返回结构里按段携带出卡点位。
  3. 中间轮正文通路：确认每一轮的 AIMessageChunk（messages 流式模式）都到达前端——特别是带 tool_calls 的轮次，其正文（正文①）也要流出来。若被过滤，查 chat_stream_service 的 messages 分支条件。
  4. 子代理 token 泄漏：SubAgent 内部 LLM 的 token 若经 subgraph 冒泡到主对话，会出现"不该出现的正文"。验证 + 按 metadata/tags 过滤。
  5. 双发去重：tool_complete 双通道（SSE 中间件 + legacy thinking_process）重发，前端已按 tool_call_id 去重——用真实数据确认商品卡不双发。
  6. 历史顺序：后端在存卡前先 flush 正文（已实现）——验证回读历史的顺序与实时一致。

5. 回答你的问题：前后端都需要优化吗？

层要不要新机制要做什么
前端渲染不需要 时序分组/卡片插入已就位按第二步清单验证；发现具体缺口再修
后端传输不需要 按轮 message_id 流式已就位第三步的通路验证（中间轮正文、子代理泄漏、双发）
后端编排/prompt要验证+可能强化条款已写（正文①/禁集中出卡），验模型遵循度，违规加 graph 兜底而非堆 prompt
mock必须重写按 §4 第一步改：加 message_id、正文①先行、卡片中途出
