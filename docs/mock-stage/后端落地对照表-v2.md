## 0. 真实链路（已核实，非推测）

```
POST /api/chat/agent/{agent_name}      body: { query, config:{thread_id, model}, meta, image_content }
   │
   └─ chat_agent()                      server/routers/chat_rounter.py:113
        │  ├─ 限流 20/60s（按 user_id）
        │  ├─ meta 注入 request_id / thread_id / user_id
        │  └─ StreamingResponse(media_type="text/event-stream",
        │        headers: Cache-Control / Connection / X-Accel-Buffering:no / CORS *)
        │
        └─ stream_agent_chat(...)       src/services/chat_stream_service.py:271   ✅ 已实现（47KB）
             │
             ├─ get_session_manager().create_session(thread_id)   sse_session_manager.py
             │
             ├─ make_chunk(content, **kwargs)                     ← 内部统一出口
             │    ├─ chunk_data = { request_id, response, **kwargs }
             │    ├─ events = legacy_chunk_to_events(chunk_data)  ← sse_adapter.py:89  ★协议翻译层
             │    ├─ edata["type"] = event_type_str(etype)
             │    ├─ session_manager.emit_nowait(thread_id, edata) ← 写回放缓冲（自增 event_id 就地写回）
             │    └─ return "".join(format_sse_event(t, d) ...)    ← SSE 文本封帧（唯一出口）
             │
             └─ yield 上述 bytes → StreamingResponse
```

**关键点**：后端**只有 `make_chunk` 一个出口**，所有事件都必须经它，否则：
- 不进回放缓冲 → 刷新页面丢事件；
- `event_id` 与缓冲对不上 → 前端拿直播 id 续传会一条都回放不出来（这段 `chat_stream_service.py:305-310` 有长注释专门讲这个坑）。

### `legacy_chunk_to_events` 是真正的协议层

`src/services/sse_adapter.py:89`。它把**旧 status 风格 chunk** 翻成 **EventType 事件**：

| 旧 chunk（`status` / `event`） | → 新事件 `event:` | 前端 case |
|---|---|---|
| `status:"init"` | `init` | ✅ |
| `status:"loading"` + content | `message_chunk` | ✅ |
| `status:"thinking_process"`, `event:"thinking"` | `thinking` | ✅ |
| `status:"thinking_process"`, `event:"tool_call"`, `tool_call.status="calling"` | `tool_start` | ✅ |
| `status:"thinking_process"`, `event:"tool_result"` | `tool_complete` | ✅ |
| `status:"thinking_process"`, `event:"plan_update"` | `plan_update` | ✅ |
| `status:"agent_state"`（含 todos） | `plan_update` | ✅ |
| `status:"finished"` | `done` | ✅ |
| `status:"error"` | `error` | ✅ |

> **这解释了为什么前端 `handleSSEEvent` 的 `default:` 分支还留着 `data.status === 'agent_state'` / `data.tool_call` / `data.plan` 这些兼容代码** —— 那是历史通道的残留，现在由 adapter 统一翻译了。

## 2. 逐项对照

### 2.1 🟡 `message_id` —— **这是最大的语义错位**

**后端现状**（`chat_stream_service.py:679-688` 注释原文）：
> `message_id` 取 LangChain 的 run id（`AIMessageChunk.id`）：同一轮 LLM 调用的所有增量 chunk 共享同一 id，不同轮次则不同。

代码：
```python
yield make_chunk(content=content, msg=msg.model_dump(), status="loading",
                 message_id=getattr(msg, "id", None))     # ← 每轮一个 id
...
yield emit_tool_call(tool_call, message_id=getattr(msg, "id", None))
```

**这个设计和前端契约其实是对齐的** —— 气泡边界 = 一个 LLM 轮次（正文 + 该轮的工具调用）。
它就是 v1 文档里反复强调的「一个气泡 = 一段前置文本 + 它引出的状态块」。

**但有几个必须处理的洞**：

| 洞 | 说明 | 影响 |
|---|---|---|
| ① `AIMessageChunk.id` 可能为 `None` | 部分 provider / 部分 chunk 不带 id | `message_id=null` → 前端落 `__local__` → **工具卡不跟随气泡** |
| ② 工具卡与正文的先后 | 若某轮 LLM 先吐 `tool_call_chunks` 再吐正文，正文会被归到同 id、挂在工具卡**之后** | 视觉上变成「状态块 → 文本」，破坏契约的「文本先行」 |
| ③ 子智能体内部的轮次 | subagent 内层 LLM 的 chunk 也带自己的 id → 会**新开气泡** | 子智能体内部过程漏到主对话，与 `task` 容器卡的设计冲突 |

**建议**：
- ① 兜底：`message_id = getattr(msg, "id", None) or f"round-{round_idx}"`，并在 `emit_tool_call` 里对 `None` 做同样的兜底（目前 `emit_tool_call` 收 `message_id=None` 会原样透传）。
- ③ 需要一层**「当前气泡 id」上下文**：主智能体轮次推进 id，子智能体内层事件一律沿用外层 `task` 那个 id。这一步和 `sse_monitor` 的注入是同一件事（见 §4.1）。

### 2.2 🟡 `plan_update` 的字段名

**后端发**（`sse_adapter.py:217`）：
```python
{"id": ..., "description"?: ..., "status": <normalized>, "toolCallIds": todo.get("tool_call_ids")}
```
**前端吃**（`applyPlanSteps`）：`steps[].id / description / status`。

- `status` 归一化已在 `_normalize_step_status` 做了（`in_progress|running|active|processing → in_progress`），✅ 对齐。
- ⚠️ 后端有个 `_todos_to_plan_steps`（:141）和 adapter 里的 `_coerce_plan_steps`（:210）**两套实现**，字段名不同（一套 `tool_call_ids`，一套 `toolCallIds`）。**应收敛成一套**，否则两条通道下发的 plan 结构会漂。
- ❌ 契约里的 `plan`（初始计划）事件后端从不发，只有 `plan_update`。前端两个 case 合并处理，所以不致命。

### 2.4 ⚠️ `_tool_meta()` 与真实 registry 是两套

`chat_stream_service.py:114` 的 `_tool_meta(name)` 是个**关键词匹配的小字典**：
```python
if any(k in lower for k in ("search","grep","find")): return {"icon":"🔎","category":"search",...}
if "task" in lower or "agent" in lower:               return {"icon":"🤖","category":"agent",...}
```

而真正的工具元数据在 `src/agents/common/toolkits/registry.py`（`ToolExtraMetadata`，`category ∈ buildin|research|analyst|critic`，`icon` 是 emoji）。

**两个结论**：
1. 前端 `BaseToolCall.vue` / `toolRegistry.js` **根本不读 `meta.icon`** —— 图标由 `tool_name` 映射 lucide 组件。所以 `meta` 是装饰性的，**不必对齐**。
2. 但 `meta.category` 前端是读的。当前 `_tool_meta` 会给 `search_products` 判成 `category:"search"`，而 registry 里它是 `"research"`。**若要按 category 分组显示，两套必须合一**；否则建议**直接改用 registry**。

## 3. 要新增的三块（真正的工作量）

### 3.1 `orchestrate` 卡 + 渐进显形

`orchestrate` 目前**不是一个真实工具** —— 后端 registry 里没有它（已 grep 确认）。
它是**契约层虚构的编排动作**，前端 `OrchestrateTool.vue` 已经按它渲染。

**两种落地方式**：

| 方式 | 做法 | 评价 |
|---|---|---|
| **A. 真加一个 tool** | 在 registry 注册 `orchestrate`，让主智能体在派活前显式调一次 | 语义干净，但要改 `graph.py` + prompt；多一次 LLM 往返 |
| **B. 由 runtime 合成**（**推荐**） | 不改 LLM。`stream_agent_chat` 在拿到意图识别结果 / 派遣决定时，**自己**用固定 `tool_call_id` 发 `tool_start` | 零 LLM 成本，且天然可控渐进节奏 |

**方式 B 的伪代码**（渐进显形：同 `tool_call_id` 连发 6 次，每次多露一个分区）：
```python
ORCH_ID = f"orchestrate-{uuid.uuid4()}"
REVEAL = ['intent','skills','rag','mcp','dispatch','decision']

def emit_orch(step: int, status: str = "running") -> bytes:
    trace = build_trace(fixture, status, upTo=step)   # 未显形分区下发空值，不省略键
    return make_chunk(status="thinking_process", event="tool_call",
        tool_call={"id": ORCH_ID, "name": "orchestrate", "args": {},
                   "status": "calling" if status=="running" else "completed",
                   "message_id": current_bubble_id},
        orchestration=trace)

for n in range(1, 7):
    yield emit_orch(n); await asyncio.sleep(0.15)
yield emit_orch(6, "completed")
```

> ### ⚠️ 两条硬规则（踩过坑）
> 1. **未显形的分区必须下发空值**（`null` / `[]` / `""`），**不能省略键**。省略会让下游分不清「还没到」和「本就没有」。
> 2. **必须复用同一个 `tool_call_id`**。前端 `upsertToolCall` 是**就地覆盖**（`orchestration: item.orchestration ?? old`），所以卡片会自动长大 —— **前端零改动**。
>
> 但注意：`sse_adapter.emit_tool_call` 里有 `emitted_tool_call_ids` 去重，**同 id 第二次发 `tool_start` 会被 `emit_tool_call` 之外的逻辑影响**。
> 实际上 `emit_tool_call` **每次调用都会重写 `active_tool_calls[id]` 并刷新 `started_at`** ——
> 渐进显形会不断重置计时，导致最后的 `duration_ms` 偏小。**渐进事件的 duration 要单独记，或让 adapter 支持「同 id 不重置 started_at」。**

### 3.2 `task` 卡 + `subagent_run`

同理，`task` 也不是 registry 里的真实工具（后端用的是 `SubAgentMiddleware`）。

**建议**：在 `SubAgentMiddleware` 启动子智能体时合成一个 `task` 卡：
```python
{
  "tool_call_id": f"task-{slug}-{run_id}",
  "tool_name": "task",
  "arguments": {"subagent_type": slug, "description": task_desc},
  "subagent_run": {
    "status": "running",
    "skills": [{"name": "..."}],
    "rag":     [{"name": "...", "detail": "...", "done": False}],
    "tools":   [],                    # 随执行逐个追加
    "plannedTools": [{"name": "...", "detail": "...", "done": False}],  # 先亮出来
  }
}
```
每次子智能体内部工具完成 → **重发同 id `tool_start`**，把新工具 append 进 `tools`、把 `plannedTools` 对应项标 `done: true`。

实测增长曲线（mock 已验证，后端照此复现即可）：
```
购前助手：已跑工具数 = [0,0,0,1,2]   已查 RAG = [0,1,2,2,2]
```

> ### ⚠️ `task` 是「容器型」，允许被夹断
> 子智能体干活期间，`task` 的 `tool_start` 会**和子智能体内部的业务工具事件交替**出现。
> 验证脚本 `pacing.mjs` 的判据已明确：**只有叶子工具**（`orchestrate` / 业务工具）要求同 id 连续；
> `task` 容器**允许**中间夹别的工具事件。后端不要为了「连续」去缓冲子工具事件。

### 3.3 ❌ `subagent_drill` —— 完全新事件

```json
{ "slug": "购前助手", "action": "expand", "description": "按偏好找候选、比价、出商品卡", "message_id": "..." }
```
- `action ∈ {expand, collapse}`
- **只写标志，不当场改展开态** —— 由 `BaseToolCall` 自己 `watch` 后改，这样用户手动折叠过的卡片不会被强行重开。
- **不切气泡**（它自己没有卡片）。
- `slug` 必须等于 `task` 的 `arguments.subagent_type`。

**产出位置**：`SubAgentMiddleware` 的「子智能体开始 / 结束」回调。
