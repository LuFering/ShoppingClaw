# 主动助理（`/assistant`）— 优化方案

> 用途：把「现状」与「目标」摊平，作为改造施工图。**本文只做设计与盘点，不含代码改动。**
> 现状全部来自代码实读 + 线上接口/DB 实测，出处标注在每张表里。
> 日期：2026-09-23

---

## 0. 核心判断（先看这三句）

**一、现状是一个纯前端演示页。** `/assistant` 的数据 **100%** 来自
`web-v2/src/apis/assistant_api.js` 里的四个硬编码种子函数
（`seedMessages()` / `brief()` / `feed()` / `todos()`）。它声明的两个后端端点
实测均为 **404**：

```
GET  /api/assistant/overview    → 404
POST /api/assistant/messages    → 404
GET  /api/events/recent         → 404      ← 首页也在等这个
GET  /api/chat/home/suggestions → 200
GET  /api/tasks                 → 200  {"data":[],"total":0}
```

页面右上角写的「在线 · 监控运行中」是**写死的字符串**（`AssistantView.vue:7`），
而 DB 里 `task_records` **0 条**（调度器空转）。卡片上的「查看证据 / 转档案 / 忽略」
只调用 `pushAi()` 说一句话（`AssistantView.vue:174-180`），
**"已把「XX」存入购物档案"是假的 —— 没有任何写入发生。**

**二、但它描述的形态是对的，而且后端零件基本齐了。** 主动助理的本质是
"把 定时任务 + 购物档案 + 对话 串成一条主动触达链路"，这三件事都已存在：

| 零件 | 位置 | 状态 |
|---|---|---|
| 定时任务 CRUD | `server/routers/task_router.py`（247 行） | ✅ 可用（但见 B2/B3） |
| 调度器 | `src/services/scheduler_service.py`（306 行） | ✅ APScheduler + Redis 锁 + 日志落库 |
| 5 类数据执行器 | `src/services/task_executors/` | ✅ 全部走 `taobao_mcp` 真实取数 |
| Agent 执行器 | `task_executors/agent_executor.py` | ✅ 能跑 MasterAgent 全流程 |
| 价格快照 | `price_snapshots` 表 | ✅ 含历史曲线接口 |
| 购物档案 | `shopping_decisions` + `/api/decisions` | ✅ 已落地，**有真实数据**（user 2: 19 条，user 7: 10 条） |
| SSE 回放 | `sse_session_manager.py`（358 行） | ✅ 断线重连 + 事件回放 |
| **结果→通知** | — | ❌ 无 |
| **事件聚合** | — | ❌ 无 |
| **对话→建任务** | — | ❌ 无 |

**三、缺的恰好是"接上"的那三段，不是"新建"。**

1. **任务跑完没人知道。** `notify_enabled` / `notify_channels` 两个字段
   **从头到尾没有任何消费方** —— 全仓 grep（排除字段定义与前端表单）**零引用**：

   ```
   $ grep -rn 'notify' src/ | grep -v 'notify_enabled\|notify_channels'
   （空）
   ```

   任务执行完只写进 `task_execution_logs`，没有任何"推给用户"的动作。

2. **通知没有出口。** `/api/events/recent` 404，所以首页状态卡
   （`AgentChatComponent.vue:337`）一直在静默降级成假数据。

3. **对话说了不算。** 16 个 buildin 工具里**没有任何创建监控任务的工具**，
   用户说"帮我盯一下价格"时 Agent 只能口头答应 —— 而界面上的"监控运行中"是假的。

**结论：本方案 = 把已存在的三段接上 + 把假数据全换成真数据。不是新建功能。**

## 1. 目标定义

### 1.1 主动助理应该是什么

一句话：**用户不在对话里的时候，系统替用户盯着、记着、提醒着。**

对应现有 UI 的三张卡，三种触达形态：

| 形态 | 触发源 | 用户看到 | 后端现状 |
|---|---|---|---|
| **命中提醒** | 定时任务执行结果（降价/补货/券/榜单/店铺） | 「石头 G20 降到 ¥2899，进入你的目标区间」+ 查看证据 / 转档案 / 忽略 | 执行器有，通知无 |
| **待确认草稿** | 购后助手归档的 `need` 阶段记录 | 「冰箱 · 海尔 501L 待你确认」+ 查看 / 稍后 | 档案表有，推送无 |
| **每日简报** | 聚合当日命中 + 待办 | 一条 09:00 的汇总 | 完全没有 |

对话区承担第四件事：**用户主动说一句**（"帮我把洗碗机加进监控"），
Agent 真的建任务 / 写档案。

### 1.2 三条设计原则

1. **PG 是唯一真相**（项目铁律，见 `AGENTS.md` 架构铁律 #1）。
   通知**不新建表**，从 `task_execution_logs` / `shopping_decisions` /
   `price_snapshots` 现算。理由见 §3.1 取舍。

2. **不引入新调度器。** 复用 `scheduler_service`，只给它加一个"执行后钩子"；
   每日简报用一条 `task_type='agent'` 的系统任务（执行器已有）驱动，
   不另起一个 APScheduler 实例。

3. **不引入常驻长连接。** 复用现有 SSE 会话回放机制
   （`sse_session_manager.event_generator` 已支持"先回放、再流式"）
   做实时推送；用户不在线时降级为轮询。不为一个低频场景上 WebSocket。

## 3. 目标架构

```
┌────────────── 触发层（已有，缺钩子）──────────────┐
│  APScheduler ──► task_executors (price/stock/coupon/rank/shop/agent)
│                        │
│                        ▼   ← 【新增】执行后发事件
│                  task_execution_logs (PG，已落)
└────────────────────────┼──────────────────────────┘
                         ▼
┌────────────── 事件层（新增，很薄）────────────────┐
│  notify_service.emit(user_id, event)              │
│    · 写 Redis List  user:{uid}:events             │
│      (LPUSH + LTRIM 200)                          │
│    · 若该用户有活跃 SSE 会话 → emit_nowait 实时推  │
└────────────────────────┼──────────────────────────┘
                         ▼
┌────────────── 聚合层（新增，无状态）──────────────┐
│  GET /api/events/recent?limit=8   → 事件流         │
│         （首页状态卡 + 助理情报流共用）            │
│  GET /api/assistant/overview                       │
│    → {messages, brief, feed, todos}                │
│      messages: 事件 → 卡片序列（实时合成，不落库）  │
│      brief:    当日聚合 + 统计                      │
│      feed:     近 N 条执行日志 → 五态               │
│      todos:    shopping_decisions(need/decided)    │
│                + 未完成 reminders                   │
└────────────────────────┼──────────────────────────┘
                         ▼
┌────────────── 行动层（新增，复用对话）────────────┐
│  POST /api/assistant/messages {text}               │
│    → 意图识别 → create_monitor_task / 归档 / 转发   │
│    → Agent 新增 create_monitor_task 工具            │
└────────────────────────────────────────────────────┘
```

### 3.1 关键取舍：通知不建表

`messages` 由事件**实时合成**（事件 id 即消息 id），"已读/忽略"状态存
Redis Set `user:{uid}:events:dismissed`。理由：

- **通知是派生物，不是事实。** 事实在 `task_execution_logs`。建表会立刻面临
  "任务被删了通知还在"、"通知显示降价但日志已过期"这类一致性问题。
- **没有跨设备同步的强需求。** 现有三张卡都是一次性动作（查看/转档案/忽略），
  不是聊天记录。
- **真要做消息中心时再加不迟。** 现在加就是过度设计 —— 与项目
  "不是单体 CRUD，优先考虑 Agent 能否用工具完成"的取向也一致。

### 3.2 事件类型对齐（不新增语义）

前端 `AgentChatComponent.vue:326` 的 `statusTypeMeta` 已有 8 种 type：
`price / coupon / stock / decide / fav / prefer / care / review`。
`notify_service.from_task_result()` 只产出其中能由任务执行结果直接判定的 4 种
（`price` / `stock` / `coupon` / `rank`→归 `price`、`shop`→归 `coupon`），
其余留给购后助手与简报。**不发明新 type**，避免前端再加一层映射。

**修法**：`notify_service` 抽出 `dismissed_ids()`，`build_feed` 读同一个忽略集合
（id 即 `log-{id}`）。忽略是「用户不想再看这条」的语义，与它从哪个出口来无关 ——
首页状态卡与助理情报流是同一批数据的两个出口，必须一致。

**验证**：`POST /api/events/log-51/dismiss` → `feed` 与卡片序列里 `log-51`
同时消失，Redis `user:2:events:dismissed` 含 `log-51`。

### 10.4 顺带修：命中类型恒为「降价」

`assistant_service.py` 原 `"hitType": f.get("result") == "hit" and "price" or "stock"`
—— 三目写死，**券/补货/榜单类命中全都显示成「降价提醒」**。

改为取 `task_type`（前端 `hitLabel` 的键恰好就是 `price/stock/coupon/rank/shop`

### 11.5 顺带修掉一个「假数据当真数据」的 bug（同 §0 第 1 点同源）

浏览器验证时发现首页状态卡**在接口成功返回空列表的情况下仍显示 4 条演示卡**，
且 `homeDemo=false`（不显示降级提示）。

根因在 `AgentChatComponent.vue` 的 `loadHomeData()`：

```js
if (events?.length) { statusQueue.value = events.slice(0,4)... }  // ← 空数组落进 else
```

`home_api.js` 已经处理对了（只有**请求失败**才给 `FALLBACK_EVENTS`，
成功且空就返回 `[]`），但组件这层用 `?.length` 判断，空数组为假 →
**演示数据原地留在屏幕上**，同时降级提示也不亮。等于把编造的
「你领的 ¥100 券明天过期」当作真实状态展示 —— 正是 `home_api.js:40`
注释自己批评过的坑，只是当时只改了 API 层没改组件。

修法：改用 `if (!demo)` 判断（失败才保留演示卡），成功且空就如实清空。

**验证**：清空事件后首页状态卡为 **0 张**（此前是 4 张假卡）；
塞入 2 条真实事件（含一个表里没有的 `unknown_kind`）后正确渲染，
未知类型落到兜底样式不崩。
