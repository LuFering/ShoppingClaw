/agent 对话执行流 · 测试指导文档

在真实后端（MasterAgent SSE）就绪前，用前端 mock SSE 驱动「开启对话 → 执行流渲染」的体验，边测边改，最后再接真后端。
当前处境（为什么这么测）
真实后端的 /api/chat/agent/MasterAgent 还不通 / 不完整（analyst、critic 工具整包缺失、/api/events/recent 未就绪等）。 但你想先调「对话开启后，思考 / 工具调用 / 正文流式」这段体验。 策略：用前端 mock 输出一段标准 SSE，喂给和真实后端完全相同的解析 + 渲染路径，把 UX 调到满意，再切真后端。这样你测的就是真实会跑到的代码，不是另写一套。

1. 执行流到底是哪条代码路径

先搞懂链路，才知道 mock 要仿什么、测的时候该盯哪。

① 用户输入点发送 / 回车
handleSendOrStop

→
② 发请求原始 fetch POST
agentApi.sendAgentMessage
agent_api.js:5
→
③ 读流response.body 按行解析 SSE（event:/data:）
AgentChatComponent.vue:1512

④ 分发handleSSEEvent 按 eventType 渲染
AgentChatComponent.vue:1184
关键事实：组件里所有渲染都只看 handleSSEEvent(eventType, data, ctx) 收到的事件类型与字段。 所以只要 mock 吐出格式正确、字段对齐的 SSE 事件，渲染路径和真后端完全一致——这是本方案能忠实测试的前提。 组件本身（AgentChatComponent.vue）一行都不用改。

handleSSEEvent 已支持的事件类型（mock 照这个发）

eventType关键 data 字段渲染到哪

thinkingcontent思考步骤池（右侧状态面板的"执行流"）
plan / plan_updatesteps计划步骤
step_start / step_completestep_id, step_name, context, duration_ms步骤卡片（running / completed）

tool_completetool_call_id, tool_name, result_preview, result_content, duration_ms工具卡片（completed）；render_product_card 会解析出商品卡
tool_errortool_call_id, tool_name, error/message工具卡片（failed）
agent_statetodos状态 + 计划步骤
titlethread_id, title会话标题（自动生成）
errorerror_type, message整轮失败（抛错，外层落为可见错误条）

注意 SSE 帧格式：解析器按 \n 切行，认 event: / id: / data: 前缀， data: 后面必须是单行 JSON。每帧形如：
event: message_chunk\ndata: {"content":"你好"}\n\n

2. Mock 方案：网络层 drop-in（最忠实、组件零改动）

在 agent_api.js 的 sendAgentMessage 里加一个 dev 分支：命中 mock 时，返回一个"会按节奏吐 SSE 的 Response"。 AgentChatComponent.vue 完全不感知——它照常读 response.body.getReader()。

代码 A — 改 web-v2/src/apis/agent_api.js

// 顶部 import 区加一行
import { mockAgentStream } from '@/mock/agentStreamMock'

// 判断是否走 mock（?mock 优先，其次 vite 环境变量）
const isAgentMockOn = () =>
  new URLSearchParams(location.search).has('mock') ||
  import.meta.env.VITE_AGENT_MOCK === 'true'

export const agentApi = {
  sendAgentMessage: (agentId, data, options = {}) => {
    // ══ 开发期：用 mock SSE 替代真实后端 ══
    if (isAgentMockOn()) {
      return mockAgentStream(data.query, options.signal)
    }
    const { signal, headers: extraHeaders, ...restOptions } = options || {}
    return fetch(`/api/chat/agent/${agentId}`, { /* …原有逻辑… */ })
  },
  // …其余方法不变…
}

代码 B — 新建 web-v2/src/mock/agentStreamMock.js

// 前端 mock：返回一个会按节奏吐标准 SSE 的 Response，
// 走和真实后端完全相同的解析 + 渲染路径（handleSSEEvent）。
const enc = new TextEncoder()
const sleep = (ms) => new Promise(r => setTimeout(r, ms))

function frame(type, data) {
  // 注意 data 必须是单行 JSON
  return `event: ${type}\ndata: ${JSON.stringify(data)}\n\n`
}

export function mockAgentStream(query, signal) {
  const stream = new ReadableStream({
    async start(controller) {
      const aborted = () => signal?.aborted
      const send = (type, data) => {
        if (aborted()) { controller.close(); return }
        controller.enqueue(enc.encode(frame(type, data)))
      }
      // 这里调用你的「场景脚本」（见第 4 节）
      await runScenario(query, send, sleep, aborted)
      if (!aborted()) controller.close()
    }
  })
  return new Response(stream, {
    status: 200,
    headers: { 'Content-Type': 'text/event-stream' }
  })
}
为什么用网络层 mock 而不是另写渲染？ 真实后端返回的就是 Response + text/event-stream 流。mock 也返回同样的东西， 组件读流的代码、streamSmoother 平滑、超时探活（IDLE_TIMEOUT_MS=120000）、停止按钮（ac.abort()）全部被真实验证。 你后面切真后端，只要把 ?mock 去掉即可，零改动。

4. 一个「真实问题」测试场景（直接可用）

⚠️ 本节场景已被修正取代：下面这份 runScenario 是「工具→卡片→文本」的旧时序， 不符合目标体验（应为：正文①开场白 → 工具 → 正文② → 卡片 → 正文③，且每轮事件要带 message_id）。 请改用《执行流时序优化方案》文档中修正后的场景脚本——两份文档配套使用，方案文档为准。

把下面 runScenario 放进 agentStreamMock.js。它模拟一个真实购物咨询，覆盖：思考 → 工具调用（搜索 + 商品卡）→ 流式正文 → 完成。

// 放到 agentStreamMock.js，被 mockAgentStream 调用
async function runScenario(query, send, sleep, aborted) {
  // —— 1) 思考过程（进右侧执行流面板）——
  const thinks = [
    '用户想给妈妈挑生日礼物，预算 800，偏好喝茶和看书。',
    '需要先找符合偏好的商品，再比价，最后给一份可执行的清单。',
    '先调用商品搜索，限定「茶 / 茶具 / 书」相关。'
  ]
  for (const t of thinks) {
    send('thinking', { content: t })
    await sleep(500)
    if (aborted()) return
  }

  // —— 2) 工具：搜索商品 ——
  send('tool_start', {
    tool_call_id: 'call_search_1', tool_name: 'search_products',
    arguments: { keyword: '茶 茶具 书', budget: 800 },
    meta: { icon: 'Search', category: '检索' }
  })
  await sleep(1200)
  send('tool_complete', {
    tool_call_id: 'call_search_1', tool_name: 'search_products',
    duration_ms: 1200,
    result_preview: '找到 12 件候选：茶具 5 / 茶叶 4 / 书 3'
  })

  // —— 3) 工具：渲染商品卡（前端会解析 result_content 出卡片）——
  send('tool_start', {
    tool_call_id: 'call_card_1', tool_name: 'render_product_card',
    arguments: { items: ['武夷岩茶', '紫砂茶杯'] },
    meta: { icon: 'Package', category: '呈现' }
  })
  await sleep(900)
  send('tool_complete', {
    tool_call_id: 'call_card_1', tool_name: 'render_product_card',
    duration_ms: 900,
    result_content: JSON.stringify({
      type: 'product_card',
      data: {
        title: '妈妈生日礼 · 茶香组合',
        items: [
          { name: '武夷岩茶 礼盒装', price: 268, shop: '张记茶行', tag: '茶叶' },
          { name: '手工紫砂茶杯', price: 199, shop: '宜兴窑', tag: '茶具' }
        ]
      }
    })
  })

  // —— 4) 流式正文（切成小片，模拟 token 流，给 streamSmoother 平滑空间）——
  const answer =
    '给妈妈挑礼物，我建议走「茶香组合」：一盒武夷岩茶（¥268）配一只手工紫砂茶杯（¥199），' +
    '加起来 467，预算很宽裕。她爱喝茶，这套天天用得上；若还想加一本字帖或散文集，' +
    '可以再补 80–120，整体仍控制在 600 内。需要我直接生成可下单清单吗？'
  for (let i = 0; i < answer.length; i += 6) {
    send('message_chunk', { content: answer.slice(i, i + 6) })
    await sleep(35)
    if (aborted()) return
  }

  // —— 5) 完成 ——
  send('done', { statistics: { total_tokens: 1280, elapsed_ms: 4200 } })
}
商品卡格式约定（来自 handleSSEEvent 的 tool_complete 分支）： result_content 解析后支持两种形状—— { type:'product_card', data:{...} } 或 { cards:[...] }。 上面用的是第一种。字段名（name/price/shop/tag）按你前端 ToolCallingResult 渲染层实际需要的来填，mock 阶段可先随意，发现渲染缺字段再补。

5. 测试清单（边测边记，每条发现都留痕）

发一条消息（空对话状态，硬刷新 :80?mock），按下面逐条核对。每发现一处不足：记一句话 + 截图，改完复测。

  1. 即时反馈：点发送后，对话区是否立刻出现"思考中…"占位，而不是等后端返回才动？（看 __placeholder__ 逻辑）
  2. 思考步骤：右侧状态面板的"执行流"是否逐条出现 3 条思考？待确认当前 /agent 布局是否有右侧面板承载 thinking；若没有，思考步骤"无家可归"——这是第一个要补的 UX 缺口。
  3. 工具卡片：search_products 是否显示 calling→completed 状态切换 + 耗时？arguments 是否人类可读（不是 raw JSON）？
  4. 商品卡：render_product_card 完成后是否真的渲染出 2 张卡，且只渲染一次？（前端对 tool_call_id 去重，mock 用稳定 id 不会双发）
  5. 流式正文：正文是否"打字机"式平滑出现？若一整段突然蹦出，说明 message_chunk 片太大或 sleep 太短，调小片长 / 加延迟。
  6. 尾字不丢：done 后正文是否完整，没有最后几个字留在缓冲里？（看 streamSmoother.flushThread）
  7. 完成态：思考中标志、工具活跃态是否在结束时正确收敛（不再转圈）？
  8. 错误路径：把场景里某条改成 event: error → 整轮是否失败并给出可重试的错误条，而不是"生成标志消失但无回复"？
  9. 停止按钮：流式过程中点停止，ac.abort() 是否真断流，已生成部分是否标"已停止"并落库？
  10. 超时探活（可选）：在 runScenario 里故意 await sleep(130000) 不吐事件，验证 120s 后走探活逻辑而非直接掐断。
  11. 工具只发 start 没 complete：删掉某个 tool_complete，验证结束时该工具被 finalizeDanglingToolCalls 收敛为"已中断"，而不是永久转圈。
最容易踩的坑： ① data: 必须是单行 JSON，多行或尾随逗号会 JSON.parse 失败被静默跳过； ② render_product_card 的 result_content 必须是字符串化的 JSON（组件里会再 JSON.parse 一次）； ③ 想看"打字效果"就别一次发整段 message_chunk，要切片 + 延迟； ④ thinking 在 /agent 当前布局可能没地方显示——这本身就是要你发现并改的不足之一。

7. 切到真实后端（最后一步，等你想接时）

  1. 关 mock：去掉 URL 的 ?mock（或 VITE_AGENT_MOCK=false）。
  2. 真实 SSE：组件会改发真实 POST /api/chat/agent/MasterAgent（带 thread_id），后端按 sse_protocol.EventType 吐事件。
  3. 字段对齐：后端事件名必须是 message_chunk / thinking / plan_update / tool_start / tool_complete / tool_error / agent_state / title / error / done——与第 1 节表格一致；不一致就在后端或前端适配器里改，不要动 handleSSEEvent 之外的渲染。
  4. 双发去重重点测：真实后端里 tool_complete 常经「SSE 中间件」与「legacy thinking_process」两条通道各发一次，前端已对 render_product_card 按 tool_call_id 去重——接真后端时务必用真实数据验证商品卡不双发。
  5. 缺口先用 mock 占位：analyst / critic 工具（G1）真后端还没有，先用 mock 的 thinking + tool 把"对比分析 / 风险评审"这段体验做出来，等后端补工具再换真实产出。
