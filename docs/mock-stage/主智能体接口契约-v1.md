# 主智能体接口契约 v1.0

> 唯一真源：`src/agent/mainAgentContracts.js`（代码即契约，mock 与真实后端共用）
> 本文是人读版。改字段名请改代码，不要只改本文。

---

## 0. 一句话定位

主智能体是**编排层**：识别意图 → 检索路由所需的最小信息 → 决定派谁 → 汇总结果。
它**不搜商品、不下单、不查物流、不读评价**。

**设计判据（决定一个能力该不该留在主智能体）**

> 「拿掉这个能力，主智能体还能不能正确派活？」
> 能 → 不该放（下放子智能体）；不能 → 该放（留在主智能体）。

凡让主智能体直接接触业务数据的，一律下放。这条判据把下面四类内容全部收敛住了。

### 编排护栏（写死在契约里，不可逾越）

| 项 | 内容 |
|---|---|
| 禁持工具 | `search_products` `render_product_card` `compare_products` `get_price` `analyze_reviews` `place_order` `query_logistics` `after_sale_service` |
| 禁碰数据 | 用户实名订单、物流轨迹、各商品售后政策、支付信息 |
| 购后边界 | 购后业务 = 购物档案（归档/阶段/提醒/复盘），**不是履约** |
| 低置信度 | `confidence < 0.6` 不派遣，先反问 |

## 1. Tools —— 4 个，全是编排动作，没有一个是业务动作

| 工具 | 渲染组件 | 作用 | 关键字段 |
|---|---|---|---|
| `orchestrate` | `OrchestrateTool`（默认展开） | 每轮调用一次，产出编排轨迹 | `arguments.decision`；结果 `orchestration` |
| `task` | `TaskTool`（默认展开） | 派遣子智能体，**唯一真正干活的动作** | `arguments.subagent_type/subagent/description`；结果 `subagent_run` |
| `todo_write` | 右侧 StatePanel 待办分区 | 把本轮计划下发成可追踪步骤 | 走 `plan` 事件，发全量 `steps` |
| `ask_user` | `AskUserQuestionTool`（默认展开） | 槽位缺失/歧义时反问 | `arguments.questions[{question_id, question, options}]` |

### SSE 时序（每轮统一）

```
thinking × N（右侧执行流，不占主对话顺序）
正文①（文本先行：识别意图 + 宣布派遣计划）
plan  { steps }                     ← 待办立即出现
正文（状态前导：说明本轮编排的判断依据）
tool_start  orchestrate             ← 编排卡「运行中」，已有 Skill/RAG/MCP/决策
tool_complete orchestrate           ← 编排卡定格，status=completed
正文（状态前导：为什么先派购前助手）
tool_start  task (购前助手)          ← 子智能体卡出现
正文（状态前导：展开购前助手）
subagent_drill { slug, action:'expand' }   ← 子智能体卡展开，内部过程可见
  ├─ 正文（状态前导：它第一件事是搜货…）
  ├─ tool_start/complete search_products      （category=购前助手）
  ├─ 正文（状态前导：收到 12 件候选…）
  └─ tool_start/complete render_product_card  （payload.type=product_card）
正文（状态前导：购前助手出结果了…）
subagent_drill { slug, action:'collapse' }  ← 收起该子智能体详情，视线交还主线
tool_complete task                   ← subagent_run.status=completed
…购后助手重复上述「前导 → 派遣 → 下钻 → 工具 → 收起」…
正文（状态前导：两路都回来了，我来对账）
正文②（拿到结果后汇总）
plan 全绿 → done { statistics }
```

## 1.5 叙述节奏（pacing）—— 硬性约定

> **每一次状态块出现之前，主智能体必须先说一段话。**

「状态块」= `tool_start`（编排 / 派遣 / 业务工具）+ 子智能体下钻 + 产物卡片。

**反例（要避免）**：一次性把「我派两个子智能体」说完，然后十几个工具状态连发，
中间再无文字 —— 用户只能看到状态在滚，不知道每一步为什么发生。

**正例**：每段前置文本都回答「接下来做什么、为什么这么做」，语言朴素、口语化，
长度 15～50 字，紧跟着的状态块就是这句话的落地。

### subagent_drill 事件（下钻）

```json
{ "slug": "购前助手", "action": "expand", "description": "...", "message_id": "round-1" }
```

| action | 时机 | 效果 |
|---|---|---|
| `expand` | 子智能体开始干活前 | 其卡片展开，用户能看到内部调用过程 |
| `collapse` | 子智能体干完后 | 收起详情，避免历史越长界面越乱 |

前端链路：`AgentChatComponent.setToolCallDrill()` 找到该 `slug` 的 `task` 卡片打上 `drill` 标记
→ `BaseToolCall` 用 `watch` 监听 `toolCall.drill` 后改展开态（**只对 expand/collapse 响应，
用户手动折叠不会被覆盖**）。

> ⚠️ `drill` 必须**同时**透传进 `upsertToolCall` 与 `to参考实现ToolCall`（双存储），否则左侧不响应。

### 实测节奏（node 直跑四个场景）

| 场景 | 文本块数 | 下钻次数 | 状态前覆盖 |
|---|---|---|---|
| 送礼 | 13 | 4 | ✓ 每个 tool_start 之前都有文本 |
| 对比 | 15 | 4 | ✓ |
| 复盘 | 6 | 2 | ✓ |
| 澄清 | 3 | 0 | ✓ |

---

> ⚠️ **最容易踩的坑**：`orchestration` 与 `subagent_run` 在两个存储层各存一份——
> 全局 `thinkingState.toolCalls`（右侧面板读）和消息级 `msgChunks[].tool_calls`（左侧对话读）。
> 加字段必须**同时**改 `upsertToolCall` 和 `to参考实现ToolCall`，否则一侧正常一侧空白。

## 2. MCP —— 5 个服务，全是「编排元数据」，不含业务数据

按接入优先级排：

| 服务 | 优先级 | 为什么必须有 | 端点 |
|---|---|---|---|
| **sc.subagent-registry** 子智能体注册中心 | **P0** | 决定「能派谁、谁健康」。没有它编排就是演的 | `list_subagents` / `health` |
| **sc.session-memory** 会话记忆服务 | **P0** | 决定「聊到哪了」。没有它每轮都当新对话 | `get_session_context` / `append_turn` / `link_record` |
| **sc.archive-link** 档案关联服务 | **P0** | 决定「有没有历史档案」→ 派购后复用还是派购前新建 | `find_record` / `list_open` |
| sc.todo-state 待办状态服务 | P1 | 多轮时待办能续上 | `upsert_plan` / `patch_step` |
| sc.orchestration-metrics 编排计量服务 | P2 | 「成本控制」skill 的数据来源 | `quota` / `record_round` |

### 注册中心条目结构（最关键的一个）

```json
{
  "slug": "购前助手",
  "name": "购前助手",
  "capabilities": ["找候选", "比价", "出卡", "横评"],
  "input_schema":  { "query": "string", "budget": "number", "forWhom": "string" },
  "output_schema": { "candidates": "[]", "picks": "[]", "risks": "[]" },
  "triggers": ["送礼推荐", "挑礼物", "对比", "值不值"],
  "not_for":  ["已下单", "物流查询", "写复盘"],
  "avg_duration_ms": 2100,
  "delivers": ["product_card", "comparison_table"],
  "health": { "status": "online", "latency_ms": 120, "queue": 0 }
}
```

> `not_for` 是**反路由**字段，防止误派——和 `triggers` 一样重要。

### 边界

`sc.archive-link` **只返回路由元数据**（`record_id` / `phase` / `thread_id`），
不返回商品与订单内容。这是护栏在接口层的体现。

## 3. RAG —— 5 个库，全是「路由与偏好」，不是商品/评价

| 库 | 优先级 | 决定什么 | doc 关键字段 |
|---|---|---|---|
| **subagent_directory** 子智能体目录（路由表） | **P0** | **决定派谁**（注册中心给"能不能"，目录给"该派谁"） | `slug/能做什么/不能做什么/入参/出参/触发意图/交付产物/平均耗时` |
| **user_profile** 用户长期画像 | **P0** | 决定**派得准不准**（给妈妈和给同事是两个任务） | `forWhom/budget_band/taboo/preference_tags/address_city` |
| history_summary 历史会话摘要 | P1 | 防重复劳动（去年送过护膝，今年别推同类） | `thread_id/date/intent/target/phase/conclusion/record_id` |
| orchestration_sop 编排 SOP | P1 | 把"送礼怎么派、对比怎么派、复盘怎么派"固化 | `intent_pattern/route/parallel/plan_template/summary_template` |
| archive_index 购物档案索引 | P1 | 判断走复盘还是重新选 | `record_id/target/phase/purchasedAt/thread_id` |

**没装、也不打算装**：商品库、评价库、物流时效库、售后政策库。理由见护栏。

## 4. Skill —— 5 个技能，全是「编排手艺」，不是业务技巧

| Skill | 输入 → 输出 | 规则 |
|---|---|---|
| **intent_triage** 意图分诊 | `{query, session_ctx, profile_hits}` → `{type, slots, confidence, need_clarify}` | 先定 type 再查 slots 缺口；缺口非空且 <0.6 → 走 clarify |
| **dispatch_orchestration** 派遣编排 | `{intent, registry, directory_hits}` → `{plan_steps, parallel, dispatch[], fallback}` | 无数据依赖→并行；有依赖（先出卡再归档）→串行并声明 `depends_on` |
| **result_synthesis** 结果汇总与取舍 | `{intent, subagent_results}` → `{summary_md, picks, rejected, risks, next_action}` | 只做取舍与收口，不重写子智能体已给出的细节；必须给 `next_action` |
| **clarify** 反问澄清 | `{intent, missing_slots}` → `{question, options[], why}` | 一次最多 3 问；每问带选项 |
| **cost_control** 轮次/成本控制 | `{metrics, intent, dispatch_plan}` → `{max_rounds, max_subagents, degrade_if_over, skip_dispatch?}` | 低置信度不派遣；已有可用结果→复用不重派 |

## 5. 编排轨迹编排结构（`orchestrate` 的载荷）

```js
{
  version: 1,
  status: 'running' | 'completed' | 'failed',
  intent: { type, label, confidence, slots: {...}, need_clarify: [...] },
  skills: [{ id, name, detail }],
  rag:    [{ id, collection, name, query, detail }],
  mcp:    [{ id, server, method, name, detail }],
  dispatch: [{ slug, task, depends_on: [], timeout_ms, parallel }],
  decision: '一句话派遣决策',
  guardrails: { touched_business_data: false, note: '...' }
}
```

`running` 与 `completed` **结构完全一致**，只有 `status` 不同 ——
所以编排卡在"运行中"就有内容可渲染，不需要等到完成。

## 6. 接真实后端的落地顺序

| 阶段 | 做什么 | 效果 |
|---|---|---|
| ① 注册中心 + 目录 | 起 `sc.subagent-registry` + 灌 `subagent_directory` | 派谁不再是硬编码 |
| ② 会话记忆 | 起 `sc.session-memory`（含 `link_record`） | 多轮接得上，档案能回跳对话 |
| ③ 档案关联 | 起 `sc.archive-link` | 能判断"这是新需求还是有档案" |
| ④ 真实意图分诊 | `intent_triage` 换成真 LLM 调用 | 置信度是真的，澄清是必要的 |
| ⑤ 计量 + 成本控制 | 起 `sc.orchestration-metrics` | 有预算概念，不会无限派 |

前 3 项齐了，编排就不再是演的。前端**零改动**——mock 和真实后端吐同一份契约。
